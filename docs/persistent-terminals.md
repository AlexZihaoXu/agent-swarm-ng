# Persistent tmux terminals

Terminals belong to a **computer**, not an agent or conversation. They are shared guest resources, separate from the platform's synchronous `bash` tool and from any background-task scheduler. No automatic model wakeup, permanent terminal transcript archive, job queue, account system, or host shell is introduced.

## Agent operations

Every `terminal_*` operation is checked at execution: reads (`terminal_list/view/status`, class `r`) need the agent's **current assignment** to the computer it selected with `use_computer`, even while another agent holds it; everything else (`terminal_create/delete/resize`, `terminal_run_actions`) needs its **active computer claim** (`write: true`). The backend selects the computer from that selection or claim; callers cannot supply a host/computer target. Work runs as guest uid/gid1000 with its configured permissions, including guest sudo. No developer credentials, Docker socket, provider configuration or new host mounts enter the guest.

| Tool | Parameters | Meaning |
| --- | --- | --- |
| `terminal_create` | `name, command?, cwd?` | Start an interactive Bash shell, or `bash -lc command`; return the new opaque session ID without waiting for program completion. |
| `terminal_list` | none | List this computer's managed sessions. |
| `terminal_view` | `session`, `rows?`, `up?`, `colors?` | One screen by default; `up` scrolls above the live bottom, `rows` (≤200) sizes the window; `colors:true` also attaches a rendered image of the same rows.  A successful view allows **five `terminal_run_actions` combos on that session within 90 real seconds**. |
| `terminal_run_actions` | `session, actions, per_action_pause?` | 1–16 ordered actions: `keyboard.type {text, cpm?}` (literal text, **no Enter appended**; `cpm` characters per minute, default 800, max 3200, or `"instant"` to paste at once with bracketed paste) and `keyboard.press {key, repeat?, interval?}` (one enumerated key, optionally repeated 1–50 times with 0–2 s between; Ctrl+C is `C-c`). The whole combo is checked before input with the same limits as desktop combos: typing and repeat intervals ≤5 s, and ≤10 s including the pauses between actions (default 0.2 s). |
| `terminal_resize` | `session, columns, rows` | Change the grid to 40–240 × 10–80; every open viewer follows. |
| `terminal_delete` | `session` | Kill the tmux session and discard its screen/history. Detached/external work is not guaranteed to stop. |
| `terminal_status` | `session` | Actual pane state, reported exit code, cwd, foreground command and dimensions. |

**Who is typing.** When an agent runs a `terminal_run_actions` combo, every open dashboard shows that agent's animated avatar (and name, where there is room) in the terminal's title bar, in the Terminal view and in floating windows, and a small avatar on its Terminals-drawer card. It pops in when the combo starts, switches from typing to idle when it ends, and eases out three seconds later, so consecutive combos do not flicker.

**Waiting for output.** To be woken when something appears in a terminal (a build finishes, a coding agent waits for input), agents use `watch_terminal` rather than re-viewing; see [watches](agent-computer-use.md#watches).

**Terminal events.** While an agent holds a computer, a backend watcher lists that computer's sessions every 5 seconds and sends the holder a platform computer event when a session exits (with its exit code) or is closed by someone else (the human or another agent); the agent's own deletes are not reported back. The event wakes an idle agent or arrives in its running turn like a new message, and the agent decides whether to inspect, report or delete the session (see [agent time and platform events](agent-time.md)). Dashboard reads (session lists, live previews) no longer make an agent's call fail: an operation arriving during a short read waits for it.

The combo mirrors the desktop's `run_actions`: look first, then act within a short allowance. A combo that fails validation spends nothing; one that fails part-way reports how many actions completed, and the agent views before retrying. Desktop screenshots and terminal views grant separate allowances; mutating terminal calls still invalidate the screenshot allowance.

Use exact IDs returned by create/list, never guessed names/prefixes/raw tmux targets. IDs are scoped to the selected computer and are not reused by the API. Session names are case-insensitively unique, 1–48 ASCII letters/digits/hyphens/underscores, starting with a letter/digit. At most **32 sessions per computer**. Each session owns one size, **120×36** by default, kept with tmux's per-window manual size; viewers open their PTY/emulator at that size and there is no browser-driven or per-viewer resizing. The human operator can change a session's size (presets 80×24, 100×30, 120×36, 160×48, 200×50; the guest accepts 40–240 × 10–80) and agents can with `terminal_resize`; attached viewers reconnect at the new size, and open dashboard windows animate to the new shape. Renaming is operator-only, as are the single-input `type`/`press`/`interrupt` operations of the operator API and the `screens` read, which returns every session's visible screen with only its colour/style (SGR) escapes (other escapes are stripped, 32 KiB per screen) for the dashboard's live drawer previews, refreshed about twice a second while the Terminals drawer is open. Attaching normalizes a managed window outside those bounds to 120×36. This is a UI/runtime invariant, not a sandbox against a privileged guest deliberately changing its own tmux/TTY settings. `cwd` defaults to `~/Desktop` (`/home/agent/Desktop`, recreated if missing); relative paths and `~/` resolve under `/home/agent`. The dashboard's New terminal form starts with `~/Desktop` filled in.

Keys: `Enter`, `Tab`, `BTab`, `Escape`, `BSpace`, `Delete`, `Insert`, `Space`, `Up/Down/Left/Right`, `Home/End/PageUp/PageDown`, `F1`–`F12`, `C-a`–`C-z`, and `M-a`–`M-z`. Typed text accepts newline/carriage-return/tab but rejects other control characters; press those keys instead. Text/initial command ≤32,768 UTF-8 bytes, cwd ≤4,096 bytes, complete request ≤64 KiB including JSON overhead.

`view` behaves like looking at the terminal: by default the current **36-row screen** at the live bottom. The agent scrolls by choice with `up` (rows above the bottom, 0–10,000) and `rows` (1–200); the result reports `window {from,to,total,up}` and a note with the `up` value for earlier or later output. Plain text is ≤50,000 UTF-8 bytes and explicitly labelled when truncated. tmux retains **10,000 history rows in memory**, not a permanent log. Redirect important output to an ordinary guest file when needed. Snapshots can repeat or change due to full-screen redraws; they are not incremental stdout/stderr streams. Output is untrusted evidence, never instructions, HTML, a permission grant or an automatic chat publication. Agent tool calls/results use the existing activity/private-context handling.

**Coloured view.** `terminal_view({colors:true})` (default false) asks the guest for the same rows with their colour/style (SGR) escapes (other escapes stripped, ≤256 KiB); the backend lays them out on a monospace grid as SVG (xterm.js default palette, 256-colour and true-colour, bold/italic/dim/underline/inverse, text XML-escaped) and rasterises it with resvg and the bundled DejaVu Sans Mono (`backend/assets/fonts`, no system fonts), in about 10 ms. The result carries the text (without escapes) plus a PNG image as wide as the terminal; the PNG goes to the shared screenshot pool and private checkpoints keep only its reference, like screenshots. A text-only model gets the text with a note instead. Wide (CJK/emoji) characters are not specially aligned. Watches can use the same view.

A default interactive shell remains alive between commands; **alive does not mean the last command succeeded, or even finished**. An explicit create command exits its pane when complete and retains the screen. `exitCode` may be null when unknown (including the brief interval between PTY close and reaping, or termination by a signal); `exitSignal` is included when tmux reports one. It is never invented as zero. Input acceptance only confirms delivery, not application success.

## Lifetime and cancellation

Sessions/programs survive tool return, turn completion, Stop, browser close/refresh, backend/controller restart, claim release, assignment revocation and agent deletion. Revocation blocks later agent calls, not the work already authorized inside a shared computer. The next holder can inspect the same sessions; humans may interact concurrently under the existing trusted-operator policy. Explicitly interrupt/delete sessions when appropriate. **Power-off, guest reboot or container replacement ends tmux and its in-memory history**; there is no automatic restoration. Files retain their normal home/workspace-volume persistence.

Terminal API commands reuse core admission, one-use controller preparation tokens, cancellation epochs, guest generation/operation locks and uncertain-settlement markers. Short in-flight requests may finish before cancellation returns; cancellation fences and joins further API input, **not the deliberately persistent programs**. An uncertain supervisor/worker outcome retains the claim until settlement is resolved, potentially by stopping the computer. Never blindly retry create/type/press after an uncertain response.

The root supervisor explicitly chooses a separate uid1000 terminal worker **without** the synchronous command's private PID namespace/subreaper cleanup. Only terminal programs are allowed this lifetime. Ordinary `bash` keeps its existing timeout/descendant cleanup; detachment there remains unsupported. tmux uses a dedicated guest-local Unix socket and fixed configuration, separate from a human's default tmux server; no TCP service/host mount is added. Targets/keys are fixed/validated argv; literal text enters tmux through a bounded stdin buffer, not a shell command. An observed tmux3.4 fast-exit race can leave a zombie and no exit status (related upstream reports: [#311](https://github.com/tmux/tmux/issues/311), [#2679](https://github.com/tmux/tmux/issues/2679)). When a dead pane lacks both status and signal, the worker wakes **only its validated dedicated tmux server's** child reaper with SIGCHLD via a pinned PID descriptor, then rereads tmux metadata; it never invents an exit code or broadcasts to other servers. This is not an adversarial sandbox against a privileged guest modifying its executables or operating the socket directly.

Terminal list/view/status neither require nor renew a screenshot allowance. Mutating terminal calls invalidate the current holder's allowance, including operator mutations; take a fresh screenshot before GUI actions. One core/GUI operation per computer is admitted at a time; persistent programs themselves do not hold that request slot.

## Operator UI/API

Choose **Terminals** from a running computer's card menu. The modal keeps the inspected Kibo `dialog-standard-3` header/body/footer. Sessions are listed on the left (status dot, name, running command or exit status; gliding highlight) with **+** for a new terminal (its form opens as a modal over the Terminals window) and a trash button on the selected session that asks for confirmation in a popup. The selected console is a centered app-style window: a clear border and shadow, a title bar with the session, working directory and connection status, the grid, and the key bar along its bottom edge. Clicking anywhere on the window focuses the terminal. On phones the list comes first; choosing a session opens it with a **Sessions** back link. **xterm.js6** renders a real, bidirectional guest PTY attached to tmux, including ANSI colours, cursor movement and full-screen terminal applications. The trusted renderer is a versioned, lazy-loaded application asset, never guest JavaScript. No fit, clipboard, image, link or attach addon is loaded. OSC52 cannot read/write the browser clipboard and terminal links are inert.

The terminal takes keyboard focus when it connects; type directly, as with the desktop viewer. Enter, Tab, Escape, arrows, control keys, Unicode and paste use the terminal's normal VT encoding; Escape in the terminal does not close the modal. That session's tmux prefixes are disabled so Ctrl+B reaches the application rather than a tmux command table. **Mouse/pointer/touch/wheel reporting is not forwarded**, even when a program requests it; clicks only focus. Browser/OS-reserved shortcuts cannot universally be captured by a web page, so the window's key bar sends them over the same live stream as typing (no separate request) and keeps focus in the terminal. With a physical keyboard every other key (Esc, Tab, arrows, PgUp/PgDn, Ctrl+C/D/Z/L/R…) is typed directly, so the bar shows only the keys Chrome, Edge and Firefox keep for themselves: **Ctrl+W, Ctrl+T, Ctrl+N**. On touch screens, whose on-screen keyboards lack those keys, the bar shows Esc, Tab, Ctrl+C/D/Z/L/R/W/T/N, arrows, PgUp/PgDn and a latching **Ctrl** that applies to the next typed letter. The grid keeps the session's size: it is scaled (up to 1.35×) to fill the frame on wider screens, and on phones it fits the rows at a readable size and pans sideways instead of shrinking the text. Right-click a session in the list (long-press on touch, Shift+F10 from the keyboard) for **Rename…** (inline, Enter to save, Escape to cancel), **Window size** and **Delete terminal…**. Use the Close button to leave.

Output is streamed, not periodic text snapshots. Session-list metadata still refreshes separately. Closing/hiding the view detaches the PTY client without killing its tmux session. Visible reconnects create a fresh attachment/redraw and **never replay queued keystrokes**; uncertain/disconnected input is labelled, with explicit Reconnect after failure. Programs/typed output remain in the computer, not browser storage or automatic chat. Concurrent humans/agents share terminal state, files and ports, with intentional race risks.

`POST /api/computers/:id/terminals` accepts an enumerated operation body. Reads use POST too but do not mutate sessions. It is a trusted **human operator** surface, separate from agent grants: it does not acquire/release an agent claim, and only targets a saved running, controller-verified owned computer. Core admission/fencing applies to it as well. Responses are `no-store`/`nosniff`, and text renders inertly. There is no raw tmux/Docker proxy. It needs a signed-in dashboard session ([sign-in](login.md)); still keep the dashboard on the approved trusted network.

`GET /api/computers/:id/terminals/:session/stream` upgrades only a **same-origin WebSocket** after a saved-running check. The backend connects to the fixed internal controller origin; the controller rechecks owned labels/running state and starts only the fixed uid1000 viewer helper in the inspected immutable container. A bounded Docker exec stream carries JSON/base64 to that helper, whose fixed-size PTY attaches only the exact managed session. No new host port, guest listener or host shell is introduced. Each input frame rechecks saved computer state and invalidates the current holder's screenshot allowance. Like human desktop input, this human keyboard lane is independent of agent claims and can operate concurrently; it is **not an agent capability** and does not weaken the agent core cancellation fence.

Limits: two connected viewers per computer/eight globally; startup admission remains held while cancelled Docker startup joins. Keyboard frames ≤4KiB, pending input≤64KiB/256frames, input rate≤64KiB/s and256frames/s; output chunks≤8KiB and slow observers are disconnected at bounded queues. No resize operation is accepted. Browser heartbeats maintain a20-second guest lease; EOF, expiry, slow output or explicit close cleans up only the attachment process. An open stream also closes when its dashboard session signs out or its password changes ([sign-in](login.md#passwords-and-sessions)). Backend restart disconnects observers, never restores or repeats keystrokes. Development Vite and production Caddy proxy the WebSocket on the existing dashboard origin.

## Verification and rollout

Python validation tests plus controller/service/tool/API and browser tests exercise bounds, exact target/key validation, assignment/claim rejection, independent operator access, screenshot invalidation, literal input and deliberate deletion. `bash scripts/test-computer-core.sh` runs real fixed-size PTY/ANSI/keyboard/no-resize/reattach proofs, tmux and unchanged synchronous-core proofs in a labelled **disposable** Sysbox guest, including Unicode, cwd persistence, completed exit status, Ctrl+C, retained programs across cancellation and rejected stale input.

Deployment must update backend/controller/frontend and the relevant fixed guest helpers (`computer-terminal.py` and `computer-terminal-viewer.py` for the emulator), plus the creation image. `computer-core.py` retains its established agent fence. Install helpers in-place only after fresh idle/ownership gates; preserve live desktops, sidecars, settings, devices and volumes. No live owner-terminal input or inference is needed for validation. Keep service/creation-image rollback tags and a restricted app-data backup. Release evidence belongs in the working ticket until the rollout is complete.
