# History and measurements

Dated rollout records, benchmark measurements and superseded decisions, moved out of the current-behavior documents so those stay accurate and readable. Nothing here describes what to do today; see [Computers](computers.md) and [Development](development.md) for that.

## Computers: trials, measurements and superseded decisions

On the actual isolated AMD64 development host, a disposable GNOME computer produced a 1920×1080 Selkies x264 stream at about 20 encoded frames per second, and a separate sandboxed Chromium browser decoded visible GNOME frames. Browser clicks opened Files and Meta opened GNOME Overview. One first frame was logged 14.8ms after its compositor timestamp; this is **not** glass-to-glass latency. A pinned ARM64 package exists, but its runtime was not tested. Separately, isolated dev API checks verified Selkies HTML and an HTTP 101 WebSocket upgrade through the existing dashboard port, two simultaneous computers, and denial of computer→media bridge/private-relay access. The embedded dashboard viewer then passed first-run portal consent with two user-initiated clicks, Chromium WebCodecs video at 1920×1080, browser pointer input opening Files, and a 320px phone surface with horizontal pan controls. Back/reopen reconnection and desktop keyboard toggling GNOME Overview subsequently passed the same isolated browser flow. A bounded input-to-decoded-video metric is reported below; the full 115-test browser regression suite passed; real Tailnet HTTPS deployment remains separately authorized and untested. The 2-CPU/4-GiB computer limit and software-encoding fallback remain. In a second isolated dev run with the one Radeon 680M render node, `vainfo` inside a non-root managed computer reported H.264/HEVC `EncSlice`, and Selkies chose **VAAPI H.264** while Chromium decoded 1920×1080. The first setup log advertised zero-copy rendering, but the real GNOME PipeWire portal supplied software frames and Selkies explicitly **demoted to readback encode**; do not describe the actual stream as zero-copy or assume a latency/CPU win without a comparison. The existing AMD Mesa driver logged a High-profile probe warning before selecting a usable VA-API profile. Twenty browser Meta-key/Overview transitions measured from input setup to the first matching decoded frame yielded **software x264 p50/p95 73.7/96.8ms** with Docker CPU **22.0/22.6%**, versus **VAAPI H.264 94.1/152.3ms** and **21.2/21.9%** on this host. These small synthetic runs include Playwright/CDP dispatch overhead and are **not optical glass-to-glass**, internet-loss, or production network measurements. With SHM readback, the GPU did not improve this low-latency workload, so hardware access stays opt-in rather than degrading the default for everyone. The live Tailnet stack now uses JPEG over HTTP on the one existing TCP port; the H.264/VA-API path remains an optional, undeployed HTTPS configuration. No agent receives computer tools by creating a computer.

**Historical Xvfb synthetic 120-Hz target / JPEG quality 50 (superseded by the Xorg dummy rollout below):** The owner selected Xvfb's `-fakescreenfps 120` synthetic Present pacing, Selkies' `--framerate=120` capture/stream target and initial `--jpeg-quality=50` (formerly 40). These are settings, **not guaranteed 120 decoded frames per second**. Xvfb has no timed physical monitor mode: XRandR still reports `1920x1080 0.00*`, **not an advertised 120-Hz display**. In isolated browser tests with quality 50, the decoder worker reported 1–19 JPEG composites per second under sparse GNOME activity, and 12 screenshot-polled Meta transitions yielded p50/p95 240/254 ms with Docker CPU p50 about 19%; neither is optical latency or proof of a speedup over the former 30-fps default. A synthetic high-damage GTK benchmark did not establish a stable paired throughput result even on the 30-fps baseline and must not be used as proof of 120-fps delivery. The owner explicitly waived a **new** backup because no work was in progress. At final preflight the prior computer UUID had already been replaced outside this rollout: the sole saved/running computer was `0fb2baf5-54c9-47e7-9d54-e6f8bb15c14a` (Workspace). Zero active agent runs were confirmed. Only that exact labelled desktop and stale media relay were replaced, reusing **its** existing named home/workspace volumes and UUID; the egress sidecar, backend, controller and frontend were not restarted. A tag for its previous X11 image was retained; earlier protected archives were made for the **former** computer and do not back up this current one's volumes. The actual Tailnet browser verified visible GNOME frames, cursor PNG/hotspot, Files click and held window drag, Meta Overview, 320px pan, and zero browser errors. Live Selkies logged `FPS: 120.0 | Mode: JPEG | Quality: 50`; its browser worker sampled sparse activity rather than sustained throughput. The dashboard still binds only loopback plus selected Tailnet IPv4 **TCP 19090**. A selectable `1920x1080@120` RandR mode needed a separately evaluated headless Xorg dummy server, adopted later (see the Xorg dummy section).

On 2026-09-25 the owner authorized this FPS rollout. Before the second desktop restart, zero agent runs were confirmed and fresh mode-0600 archives of `.local` plus both exact named volumes were written to the mode-0700 `.local/backups/` directory and integrity-checked (the earlier no-backup waiver was explicitly limited to the previous GPU/DPI restart); those three archives were removed on 2026-09-26 after the owner deleted that same Workspace from their own Tailnet device, while the rollback image tags stayed. Only the controller and this owned desktop were replaced; the stale owned media relay was recreated, while backend, frontend, egress gateway, `.local`, UUID `e01621c4-3c9a-4e10-a116-26c9e934da78` and both named volumes were preserved. Old desktop/controller **image tags** remain (`agent-swarm-default:pre-xorg120-20260925`, `agent-swarm-ng-computer-controller:pre-xorg120-20260925`). After migration the guest still maps only `/dev/dri/renderD128`, has no card device or published port, and its home files survived.

Measured live over Tailnet HTTP/JPEG with a continuously redrawing 1600×900 guest canvas: Selkies encoded about **110–120 fps** (previously ~61 on Xvfb) and the pinned decoder worker presented a median **129** composites/s in a nine-second window, with bursts and intervals where the server reported `throttled=true` at ~155–168 Mbps. So heavy motion now genuinely exceeds the former ~60 ceiling, but delivery is **not** a smooth guaranteed 120 and costs more CPU and bandwidth; an idle or sparsely changing desktop still sends only a few frames per second because JPEG is damage-driven. A separate bounded window-drag probe was inconclusive because it did not create sustained damage. These are headless-Linux-browser counters, **not** optical glass-to-glass latency or proof of 120 Hz on the owner's physical display. A disposable full regression and a fresh live Tailnet browser session also verified visible AMD RADV WebGL, guest-only Ctrl+T/Ctrl+W through **Send keys**, GNOME PNG cursor/hotspot, phone pan, zero browser errors, and a DPR-2 client whose `scaling_dpi` 192 request the server rejected against `['96']` while guest Xft resources stayed **unset before and after**. Test-only guest fixtures and their Chrome processes were removed afterwards. HEVC/AV1 remain unavailable: this host encodes HEVC but only decodes AV1, and the insecure HTTP origin has no WebCodecs.

On this host `vainfo` for the Radeon 680M reports **HEVC Main/Main10 hardware encode** (`EncSlice`) but AV1 **decode only** (`VLD`), not AV1 hardware encode. Selkies provides H.265 and AV1 full-frame codecs over WebSockets/WebCodecs or WebRTC, but the deployed Tailnet HTTP viewer only decodes its pinned JPEG/createImageBitmap fallback; browser WebCodecs are unavailable without a trusted secure origin. The Tailnet account has previously rejected TLS certificates. At the time, selecting HEVC **without** browser capability negotiation would have broken the HTTP viewer, and software AV1 on a two-core desktop was not demonstrated at 1080p120. The later H.265-default image keeps HTTP JPEG and secure H.264 fallbacks (see the codec rollout below); this earlier investigation is not a description of the current creation default. In a disposable Sysbox computer with only `/dev/dri/renderD128` mapped, sandboxed Chrome initially ran WebGL through software SwiftShader. The staged X11 variant now includes Mesa RADV and a grant-gated GNOME Chrome launcher that selects ANGLE Vulkan **with software window compositing** (`--disable-gpu-compositing`, no sandbox/blocklist bypass): Xvfb cannot present the hardware canvas with GPU compositing. A disposable real guest GUI Chrome reported `ANGLE (AMD, Vulkan ... Radeon 680M ... radv)`; its WebGL fixture only shows the green shader when the renderer is AMD and not SwiftShader/llvmpipe. The separate Tailnet-style HTTP/JPEG browser saw 38,121 shader-green pixels; its trusted shortcut menu opened a guest tab (38 green pixels, one host tab) and closed it to restore 58,140. DPR2 did not change that disposable computer's initially **unset** Xft DPI; GNOME scale and 1920×1080 stayed fixed. Full Files click/drag/Meta/phone pan and portal-free mock2/2 passed; test-owned resources were deleted. This proves GPU-backed guest WebGL and remote visual delivery in that isolated case, **not** improved stream encoding, CPU, latency or 120 delivered fps. The render-node grant exposes the host GPU driver to a sudo-capable computer and is an explicit operator risk choice. The owner approved a **combined** GPU/DPI desktop/controller restart and waived a new backup for **this** restart. A disposable old-X11/no-GPU→GPU/DPI rehearsal preserved the same UUID and home/workspace sentinels across controller/device-grant change. Immediately before live mutation, the sole saved/running Workspace was UUID `e01621c4-3c9a-4e10-a116-26c9e934da78`, with zero active agent runs, exact managed labels and its two named volumes. Only the controller and that owned desktop were restarted; the stale owned media relay was replaced to follow the new private IP. Backend/frontend, egress gateway, `.local`, UUID and named home/workspace volumes were not replaced or deleted. Old desktop/controller **image tags** remain for rollback; no new data backup was made per the owner's waiver. The now-running Sysbox desktop maps only `/dev/dri/renderD128`, has no card node or published port, and the operator's persisted project-local Compose setting is restricted to that node. It retains JPEG/TurboJPEG over Tailnet HTTP; the GPU grant enables guest Chrome WebGL, not hardware JPEG encoding. A real Tailnet DPR-1 browser saw 58,178 green shader pixels from AMD RADV WebGL, Ctrl+T opened only a guest tab (11 green pixels; one host tab), Ctrl+W restored 58,140 pixels, with a GNOME PNG cursor and no browser errors; DPR-2 phone pan also passed. Selkies rejected its DPI192 proposal (`allowed list ['96']`), Xft resources stayed unset, fixed 1920×1080 and Mutter/text scale 1.0 persisted, and loopback plus the chosen Tailnet IPv4 remained the only **TCP19090** bindings (zero UDP). The temporary test Chrome profile and fixture were removed from guest `/tmp`; no user-volume files were touched. This is not a claim of 120 delivered fps, lower latency or HEVC/AV1 stream support.

Measured on a throwaway computer from the separate `agent-swarm-default:h264-xorg120` image (built from `stage2` through `x11.Dockerfile --build-arg COMPUTER_STREAM_BASE=…`): the HTTPS origin negotiates **VAAPI hardware H.264** (`Encoder: VAAPI | Mode: H264 | CRF: 25 | VBV: 8000 kbps`) at ~100 fps with `VideoDecoder` present, versus **CPU JPEG stripes** (`Encoder: CPU (x264) | Mode: JPEG | Quality: 50`, no bitrate cap) on HTTP. H.264 hardware encode covers Baseline/Main/High plus HEVC Main/Main10; AV1 remains decode-only on this host.

## Development: rollouts and migrations

An earlier Bun 1.3.6 Docker build crashed during backend Prisma generation, requiring a host-specific checksum-matched dependency/runtime-layer workaround. During the **2026-09-24 stage-1 Computers rollout**, the regular production Docker Compose backend build succeeded (with cached layers) and passed an isolated production-image migration/health smoke test before replacing the live image; the old workaround is not a checked-in replacement for `backend/Dockerfile` or a promise that future cold builds succeed. For backend source or schema changes, regenerate the client, build and smoke-test a new backend image before restarting; never reuse a frontend-only shortcut for a changed backend. For frontend-only changes to the **current** portal-free Tailnet HTTP/JPEG stack, include all **four** overlays in both commands: `TAILSCALE_IP="$(tailscale ip -4)" docker compose -f compose.yaml -f compose.tailscale.yaml -f compose.tailscale-http-jpeg.yaml -f compose.tailscale-http-jpeg-x11.yaml build frontend`, then `TAILSCALE_IP="$(tailscale ip -4)" docker compose -f compose.yaml -f compose.tailscale.yaml -f compose.tailscale-http-jpeg.yaml -f compose.tailscale-http-jpeg-x11.yaml up --no-build --no-deps -d frontend` after checking live runs. Omitting either JPEG or X11 overlay would select an incompatible capture/consent mode.

The stage-1 rollout checked `/api/events` for zero active runs, stopped backend/frontend for a consistent mode-0600 `.local/backups/` archive including WAL and credentials, applied the additive computer migration, and verified the existing agent/message counts and only loopback/Tailnet TCP 19090 binding. It did **not** create/delete a computer on the live data stack or run a browser against the live site. The 2026-09-25 stage-2 Tailnet HTTP/JPEG rollout again checked zero active runs and saved counts, stopped backend/controller and the one running stage-1 desktop with owner approval, saved fresh protected archives of `.local` and both named volumes plus local image rollback tags, then replaced only the desktop image. Its UUID, named home/workspace volumes, GNOME preview and saved Agent/Message/Computer/Migration counts (1/6/1/11) survived. The live dashboard served a valid static viewer, patched trusted JS, restricted JSON/API paths and an HTTP 101 media upgrade on only loopback plus Tailnet TCP 19090. A dedicated Linux browser confirmed HTTP is an insecure origin and create-computer dialogs center at 1280/320px without creating any live computer. The operator did **not** auto-click GNOME's first-run screen-sharing dialog; visible live frames/input on this user computer remain unconfirmed until the human viewer grants consent. This is **not** a public deployment: the platform has no user authentication, and every Tailnet peer allowed to reach it can operate it. The Compose **platform services** use `restart: unless-stopped`; managed desktop/egress/media containers use Docker `RestartPolicy=no` instead. An OOM-killed child need not stop its desktop, and a stopped desktop is not automatically restarted by Docker or continuously monitored by the controller; see [resource limits and OOM](computers.md#resource-limits-and-oom). Verify the Tailnet URL after reboot, since binding its IPv4 depends on the interface being ready. Never expose port 19090 to a public interface.

The later **portal-free X11 migration** was approved by the owner for Swarm-owned containers (not data deletion). The new tracked isolated harness passed genuine remote HTTP/JPEG browser video, GNOME cursor, Files click, held window drag, Meta keyboard and phone pan; the original Wayland API + eight real browser tests and all 185 unit/integration tests passed. A separate disposable stage2 JPEG→X11 rehearsal preserved home/workspace sentinels, UUID, isolation and rollback. Immediately before the live restart `/api/events` again showed zero active runs; the backend was stopped for a fresh mode-0600 `.local` archive, then controller and owned desktop stopped for separate protected home/workspace archives. A stopped-container/overlay rollback image and all prior service-image tags were retained. Only the owned stale media relay was removed; the new X11 desktop reused the named volumes, and the old stopped duplicate container was removed without `-v` after preview and media checks. The portal-free frontend was swapped last, without restarting the new GNOME session. Live Tailnet Chromium then confirmed frames, exact cursor image/hotspot, real click+drag+Meta and mobile pan with zero logged browser errors; the upper-right screenshot band had zero orange share-indicator pixels. Backend/controller/frontend remained healthy, saved counts were **1/6/1/11**, and only loopback plus Tailnet IPv4 bound TCP19090. The owner still needs to judge their own device's feel; the measured JPEG latency does not establish a speed gain. Do not remove the restricted backups/rollback images without owner approval; never silently switch to a public bind. A post-rollout audit found **old live gateway/media sidecars** had inherited `com.docker.compose.project` labels from shared images built under earlier disposable test projects, even though their authoritative `swarm.ng.namespace` is `agent-swarm-ng`. Direct-build the shared egress/media image tags (now clean), and the controller refuses such image metadata on future child creation. Test cleanup checks for foreign managed namespaces before `compose down`; never delete a live sidecar based only on its inherited Compose-project label. Replacing the already-running gateway to remove its historical label would stop the desktop under the controller's filtered-egress recovery rule; coordinate that separate maintenance rather than doing it as cosmetic cleanup.

The later owner-approved **GPU/DPI X11 replacement** retained the same Workspace UUID and named home/workspace volumes. This time the owner explicitly waived a new backup; that waiver is not a standing policy for future restarts. The old desktop/controller image tags were retained locally. The operator's ignored, mode-0600 project `.env` now fixes `COMPUTER_RENDER_DEVICE=/dev/dri/renderD128`, while the new X11 image locks Selkies to DPI96. Do not omit that Compose setting during future controller recreation: a mismatch intentionally stops the owned desktop rather than leaving a revoked device grant running. A disposable old-X11/no-GPU→GPU/DPI migration rehearsal and live DPR-1/DPR-2 Tailnet/WebGL checks passed. That guest still used Xvfb, whose virtual monitor advertises no timed refresh rate; the Xorg dummy rollout below replaced it. See [Computers](computers.md) for precise acceptance and the insecure-origin HEVC/AV1 limitation.
