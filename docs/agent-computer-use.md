# Agent computer use

Status: deployed to the trusted dashboard from `6cfb464` on 2026-09-27. This capability is separate from human desktop viewing, agent identity and channels. The dashboard itself needs a sign-in ([login](login.md)). Computer assignments start empty and are set explicitly by the human.

## Assignment and control

In an agent's settings, **Computers** selects its allowed desktops from preview cards (live thumbnail, name, running state, check badge; each card is a labelled checkbox). Assignments save with the rest of the page (one Save changes) and survive restarts. Multiple agents can be assigned the same computer. **Anyone reads, one writes.** `use_computer({computer: idOrName})` selects a computer to read: `glance`, `look_at`, file `read`, `terminal_list/view/status` (and `save_screenshot`) work with only the assignment, even while another agent holds the computer, and never disturb the holder; a reader waits out the holder's running operation instead of failing, and its looks grant no input allowance. `use_computer({computer, write: true})` claims it (one holder per computer, one computer per agent) for everything that changes it: desktop and terminal input, `write/edit/bash`, terminal create/resize/delete, watches and monitors; it is refused, naming the holder, while another agent holds it. `write: false` gives up the claim and keeps reading; omitting `write` on the computer already held keeps the claim; selecting another computer gives up the claim on the old one; `{computer:null}` releases everything. Reading selections live in memory (a restart clears them with the claims). `list_computers` lists assigned resources, holders and what the agent reads. The viewer header shows the holder and, apart from it, the agents reading the computer as overlapping avatars (`GET /api/computers/control` returns `holders` and `readers`). Names resolve to a stable ID; a held destination leaves the old claim intact. Checks run at execution, not just when a tool is displayed. Every tool declares what it does (`r`, `w`, `rw`, or `claim` for `use_computer`; `backend/src/tool-access.ts`), and `help` lists an agent's tools by class.

A blocked agent asks the current holder to release via an already-permitted conversation, or asks the human for **Force release** in the viewer. No new messaging grant is implied. Force release cancels and settles input before releasing/transferring the claim, while preserving assignments and the agent's reading selection. Unknown cancellation settlement fails closed. Agents release when finished unless the human explicitly asks to retain a dedicated computer. The human can interact concurrently; those cursor/focus races are deliberately accepted.

**File copies are the exception to control.** `copy_file` and `upload_file` move whole files into or out of a computer with only the assignment: they never take or need the claim, are not refused because another agent holds the computer, and tell the current holder about the copy with a platform computer event. See [Agent files](agent-files.md#copying-files).

A Swarm backend restart cancels/settles persisted claims, releases them, clears screenshot allowances and leaves an agent-facing notice for each affected agent's **next normal turn**. It does not automatically wake inference or replay interrupted work. Browser refresh merely reattaches observation and does not release claims. Revoking an assignment releases active control; deleting an agent cascades its assignments/claim and archive.

The human viewer starts **Input locked** (the header's lock icon) each time it opens/reconnects; on an upright phone, where the desktop is shown turned, it stays locked. The actual guest cursor is composed into the shared video stream, so locked observers can see agent/remote pointer motion. All trusted viewers use that same cursor mode, with the duplicate local CSS/canvas cursor suppressed; unlocking or detaching one viewer does not turn off another viewer's cursor. The toggle only enables/disables human pointer/keyboard/touch/shortcut input; it does not stop video, release an agent or revoke assignments. This adapts the v2 idea, not its overlay-only implementation: the trusted iframe also gates input events and shortcut messages after focus.

## Observe, act, verify

- `glance({quality?: "low"|"medium"|"high"|"full"})`: fresh full-desktop JPEG at 33% (default), 50%, 75% or 100% native dimensions. Low is for orientation, not accurate reading. Use high for broad readable context, full for exact text/fine details across the screen, or native `look_at` for a particular region. If text is unclear, increase detail/crop rather than guess or repeat low-resolution views. Verify the actual application result at adequate detail before claiming success. Existing JPEG/frame limits apply; use a crop if a full frame exceeds them.
- `look_at({x,y,size})`: native-resolution crop with center and radius in **[0,999]** coordinates. Each axis shifts into the screen while preserving its span, or becomes the full [0,999] axis if oversized. Return actual pixel-rounded normalized bounds plus output dimensions, not just the requested rectangle.
- `run_actions({actions,per_action_pause?})`: a validated ordered combo, at most 16 actions. Action entries use `{name,params?}`. Recommended pause defaults to 0.2 seconds, **only between** actions. Every key/button down must pair with an up in the same combo, without duplicate downs or unmatched ups.

Each successful `glance`/`look_at` resets **two combos for 30 real seconds**, per agent and claimed computer. Failed screenshots do not reset it. Invalid/preflight-rejected combos consume no use, but time still elapses; started partial failures consume a use. Release/switch/restart invalidates the allowance. An expired/exhausted allowance errors before input and tells the agent to look again. This bounds blind operation; it cannot freeze a desktop or remove human races.

Actions: `mouse.move_to` (x,y,speed), `mouse.left_click`, `mouse.right_click`, `mouse.down/up` (button left/middle/right), `mouse.scroll` (direction and whole detents), `keyboard.down/up` (documented X11 key name), and `keyboard.type` (text,cpm). Movement uses physical endpoint distance at 8000 px/s by default, maximum 24000; a bounded Bézier trajectory is computed for that duration. Typing defaults to 800 CPM, maximum 3200, counting Unicode scalar codepoints, not bytes/graphemes. There is no additional product text-length cap: calculated duration limits it. Ordinary bounded transport bodies still apply. Type rejects unsupported control characters and combo-held keys. Click/scroll-detent dwell is 0.02 seconds.

Reject the **whole combo before any input** if invalid or above 5 seconds of action time / 10 seconds including pauses. The controller and guest repeat validation. Runtime power loss, app behavior and transport failure can cause partial effects; return partial progress and do not retry blindly. Guest cancellation uses a generation fence plus operation lock/cleanup, not just HTTP abort, so a delayed old request cannot act after Force release. Only labelled owned computers are targets; no host input/shell is exposed.

## Guest file and shell tools

Custom `edit`, `write`, and synchronous `bash` run only in the agent's **currently assigned and claimed computer**; `read` needs only the assigned computer it reads. Merely being assigned does not authorize a change. Their Pi names override the development harness's built-ins; no platform-host tools are enabled. The backend resolves the target from the claim, never from a caller-supplied computer ID. File contents and command output are untrusted evidence. No developer/provider credentials, Docker socket or new host mounts are inherited.

- `read({path,offset?,limit?})`: regular UTF-8 text files, 1-based lines. One call returns a page of 200 lines by default; a larger `limit` (at most 2,000 lines/50,000 returned UTF-8 bytes) is the agent's explicit request. `nextOffset` scrolls down and `prevOffset` up. Invalid bytes are replaced for display. Explicit `truncated`, `partialLine`, `nextOffset` and `prevOffset` metadata; a partial long line needs a bounded shell extraction. Offset scans stop at 32 MiB. PNG/JPEG/GIF/WebP/BMP images use real model image blocks, first frame only, at most 4,096 pixels/axis, 16 million pixels, 2 MiB returned image (16 MiB input). Image decoding permits local file/pipe protocols only. File images share the existing capped pool/private-session references; they are not desktop observations.
- `write({path,content})`: create parents and atomically replace one UTF-8 file. New files are private; existing permissions are preserved.
- `edit({path,edits:[{oldText,newText}]})`: 1–100 unique, disjoint exact matches against the original UTF-8 file. All matches validate before replacement. Target/result at most 16 MiB. Detects observed concurrent changes, but is not a filesystem-wide lock against a human editor.
- `bash({command,cwd?,timeout?})`: fresh noninteractive Bash, default 30 seconds, maximum 120. Returns exit status plus separate stdout/stderr tails, each at most 25,000 UTF-8 bytes/1,000 lines. Truncation is explicit; redirect needed output to an ordinary guest file and read it. Cancellation/timeout can lose final output, and never undo committed side effects.

**Read windows.** No read-like agent tool returns a large body unless the agent asks for it. Like a person scrolling, the agent sees a page and chooses where to go next: `read` shows 200 lines (`nextOffset`/`prevOffset`, larger `limit` on request), `terminal_view` shows one 36-row screen (`up`/`rows` scroll through scrollback, ≤200 rows), chat history tools return bounded sections with cursors and per-message character offsets, Knowledge reads take a `length`, and web fetches return 30,000 characters inline with `get_search_content` offsets. `bash` returns bounded stdout/stderr tails; larger output belongs in a file that `read` pages through.

All requests are bounded to 64 KiB including JSON overhead. Relative paths, `~/` and the default `bash` cwd use `/home/agent`, the persistent home (`/tmp` is disposable, wiped at every computer start; see [computers](computers.md)); absolute paths remain inside the guest filesystem. Working directory/environment changes do not persist between commands. Work runs as the guest `agent` account with a minimal environment and its configured permissions, including guest sudo. This is broad computer access, **not** a restricted-path or hostile-guest sandbox. In particular, shell access can modify files and interact with applications without the GUI combo interface; the screenshot allowance is not a shell security boundary. Core calls do not require or renew that allowance, and `bash`/`write`/`edit` invalidate it before further GUI input.

The controller uses one-use preparation tokens and cancellation epochs, separately from the guest generation fence. Already-admitted Docker execs are joined before cancellation is acknowledged, including delayed delivery. A fixed root supervisor starts the unprivileged worker in a private PID/mount namespace using existing Sysbox privileges (no extra host capabilities). The worker is PID 1; its exit kills detached descendants. `ps`/`/proc` therefore show that command's processes rather than existing desktop processes. Subreaper cleanup and PID-file-descriptor signalling avoid ordinary orphan/PID-reuse races. A root-owned active marker makes lost-supervisor settlement fail closed: control remains held; a human may need to stop the computer before release. This synchronous bash tool provides no persistent shell or automated desktop restart. The separately granted [tmux terminal tools](persistent-terminals.md) deliberately allow persistent programs; their short API calls reuse the core fence, but cancellation/release does not kill those programs. Agents must not use service/daemon launch or detachment to evade the synchronous lifetime. Work handed to an existing external service, and deliberately privileged guest tampering, cannot be rolled back or contained by that lifetime; this does not provide adversarial isolation between users sharing a privileged guest.

Opt-in real runtime check (Linux/Docker with Sysbox and a built desktop image): `bash scripts/test-computer-core.sh`. It creates and removes only a labelled disposable guest with the managed desktop's process-security settings; it never accesses the owner's desktop or credentials.

## Persistent terminals

The `terminal_create/list/view/status/resize/delete` tools and `terminal_run_actions` (typing and key combos after a `terminal_view`) operate on shared tmux sessions in the same currently claimed guest. They do not change synchronous `bash` semantics. Sessions survive turns, Stop, browser/backend/controller restarts and release/revocation, but end when the computer stops; no automatic restoration or background-job scheduler is provided (agents can wake themselves with [timers and reminders](agent-time.md), and hear about terminals that exit through computer events). Operator **Terminals** opens a fixed-size real PTY emulator with direct keyboard input (no mouse forwarding) without taking a claim. This human keyboard lane is concurrent like human desktop input; agent tools retain their existing claim/cancellation fence. See [persistent terminal semantics, bounds and rollout](persistent-terminals.md) and Swarm Knowledge `concepts/computers/terminals` / `practices/terminals` before use.

## Watches

`watch_terminal({session, until, every_seconds?, timeout_seconds?, check_now?, context?})` and `watch_desktop({region?, until, …})` let an agent wait for a condition on the computer it holds without keeping a turn busy. They are **one-shot** by default: the first check that finds the condition wakes the agent once and the watch is removed. With `repeat: {cooldown_seconds?, max_fires?}` a watch keeps going: it fires once per occurrence (it re-arms after a check no longer sees the condition; a yes on a view changed since the last firing, with a different report, also counts as new), checks nothing while the agent's turn that received a wake-up is running (the broker hands the watch that run's completion; the deadline still ends it), wakes the agent at most once per cooldown (default max(60 s, interval); firings in between merge into one event), tells the watcher its last report, spaces checks a full interval after each other however long one took, survives two failed checks in a row with growing pauses (the third ends it), and ends at `max_fires` (default 20, max 100) or its timeout.

`monitor({command, timeout_seconds?, max_events?})` runs a command in the held computer and wakes the agent with its stdout lines, with no model call. The controller (`POST /computers/:id/monitor`) runs it with `docker exec` as `agent` in `/home/agent` under a small wrapper: the command runs in its own session (`setsid`), and when the stream closes the wrapper kills that whole process group; when the command exits on its own, its exit code and last stderr come back as a final `\0exit {code, stderr}` line (accepted only as the stream's last line). The controller writes a `\0ping` heartbeat every 30 s and disables its idle timeout for the stream, and the backend fetch has none, so a quiet command is not mistaken for a dead connection. The backend (`computer-use/monitors.ts`) batches lines printed within 200 ms, keeps at most one pending wake-up per monitor (newest 20 lines shown, older ones counted), holds output while the agent's turn that received the last wake-up runs, stops immediately when its computer's claim ends (`ComputerUseService.onClaimEnding`, before the claim is cleared: the agent is told on a force release, nothing on its own release), re-checks the claim every 15 s as a backstop, and stops at its timeout (default 1 h, max 24 h), `max_events` (default 50, max 500), more than 300 lines in 10 s, the command's exit, or claim loss; the agent is told why. Releasing the computer and `cancel_timer` stop it quietly; `list_timers` lists monitors with watches (at most 3 of each). Monitors share the watch table so a restart tells their agents they stopped.

- **Checks.** Every `every_seconds` (30–3600, default 30; first check immediately unless `check_now:false`) the backend reads the view (terminal text with its running/exited state, or a screenshot of the screen or of a `{x,y,size}` region) and runs a short model check on the agent's **own model**. The watcher gets the agent's condition (`until`, ≤1000 characters), the current view, the view at watch start (when it differs), and whether the view changed since the last check or for how long it has been unchanged. Nothing is skipped because it is unchanged; the unchanged duration is fed in instead. It may look closer with look-only tools (terminal view incl. colours/status, or glance/look_at bound to the watched computer and terminal), has at most 10 model turns and 120 s, and answers in plain text `NOTIFY: …` or `KEEP_WATCHING: …`.
- **Fresh or fork.** `fresh` (default) uses a small watcher prompt. `fork` (only with `every_seconds` < 150) continues a copy of the agent's own conversation: the request keeps the main session's exact system prompt, tool list and session ID (the provider prompt-cache key), so the cached prefix is reused; only the watcher's read tools execute, others are refused, and the decision is text so no tool is added. The fork basis is the live session while a turn runs, otherwise the session as its last turn ended (kept only while the agent has fork watches).
- **Endings**, each removing the watch and (except the agent's own) waking the agent once with a platform computer event: fired (with the watcher's report), timed out (default the larger of 600 s and 10 × interval, max 24 h), a check failed (model/computer error: the agent is told in case the condition happened, like triage's interrupt-on-failure), the watched terminal is gone (closed by someone else or unviewable), the computer was lost (force release even if reclaimed, assignment removed, powered off, or blocked as uncertain; the event says what to do next), a desktop watch whose model no longer accepts images, or a platform restart. The agent's own `cancel_timer`, releasing/switching computers (even mid-check) or deleting the watched terminal ends watches quietly. Every watch gets at least one check before it can time out; fork checks get 240 s instead of 120 s, and both cap output at 4096 tokens. A failed read-only watch operation never marks the computer as uncertain.
- **Bounds and safety.** At most 3 per agent; checks never overlap and wait for a busy computer instead of failing; they grant no input allowance (screenshots taken by watchers never enable `run_actions`); desktop watches need a vision model. `list_timers`/`cancel_timer` include watches. Each check is its own entry in the agent's activity log (`Computer watch check`).
- **Restarts.** Watches live in memory because a restart releases every claim. A `ComputerWatch` row exists only so that, after a restart, each agent is told once that its watch ended.

## Harness listeners

When an agent drives a coding harness (Claude Code, Codex, OpenCode, Pi) in a terminal, it listens to the harness's own events instead of watching the screen.

- **Harness assist** ships in every computer image at `/opt/swarm/harness-assist` (read-only for the agent user). The agent installs the adapter for a harness with the human's consent, the first time it is about to drive it on a computer without it: `/opt/swarm/harness-assist/install <claude-code|codex|opencode|pi>` (`--status` shows which have it, `--remove` uninstalls). A refusal is remembered (memory). The system prompt calls it highly recommended and sends the agent to Knowledge (`practices/harnesses`) before asking.
  - Claude Code: a local plugin marketplace (`claude-code/`) with the plugin `swarm-assist@swarm` (user scope): async hooks for Stop, StopFailure, PermissionRequest, Notification (idle, elicitation, agent input), SessionStart/End, and a stdio MCP server.
  - Codex: a marked block in `/etc/codex/config.toml` (the system layer, written with sudo, so its hooks need no per-user `/hooks` trust review): hooks for Stop, PermissionRequest (log-only: exit 0, empty stdout, so the approval prompt still shows), SessionStart/End, and the MCP server with `env_vars = ["TMUX", "TMUX_PANE"]` (Codex clears an MCP server's environment) and `approval_mode = "approve"`. Codex has no events for API failures or model questions. Codex itself runs unsandboxed on every computer: its bubblewrap sandbox cannot start inside one (the computer is the sandbox), so the image ships `/etc/codex/config.toml` with `sandbox_mode = "danger-full-access"` (`codex/system.toml`), and the installer adds it first on older computers unless a `sandbox_mode` is already set. Computers made from an older image get it only from that installer, from adding the line themselves (Knowledge tells agents how) or by updating to the latest image. Codex may also show "Cannot use the background server" at startup (its shared app-server daemon is unavailable); "Run without daemon this time" works, and Knowledge says so.
  - OpenCode: a plugin in `~/.config/opencode/plugins/swarm-assist.ts` (and `@opencode-ai/plugin` in that folder's `package.json`): `session.status` idle (with the last completed text), `permission.asked` (observed; OpenCode never calls a plugin to answer it), `question.asked`, `session.error`, `session.created`, and a `notify_supervisor` tool.
  - Pi: an extension in `~/.pi/agent/extensions/swarm-assist.ts` (global extensions need no trust prompt): `agent_settled` (finished, or failure when the last assistant message stopped on an error), `ui_prompt_start` (question), `session_start`/`session_shutdown`, and a `notify_supervisor` tool. Pi has no permission prompts.
- Every adapter writes one compact JSON line per event, through the shared `harness_event.py`, to `/run/user/1000/swarm-harness/events.jsonl` inside the computer: harness, event (`finished`, `permission`, `question`, `idle`, `failure`, `session_start`, `session_end`, `message`), terminal (tmux `TMUX_PANE` → `sw-<id>` and `@swarm_name`), session, cwd and at most 300 characters of text. Hooks print nothing (an empty output is "no decision"); tool-call events are never written.
- `notify_supervisor({message})` (`supervisor_mcp.py`: an MCP server for Claude Code and Codex, `--notify` for the plugins) writes a `message` line only when a listener covers that terminal (otherwise the harness is told nobody is listening and to try later), at most one per 10 s and 30 an hour per terminal, 1000 characters.
- `harness_listener_add({terminal, events?, computer?})` (w) needs only the assignment (anyone reads). Defaults: finished, permission, question, failure, session_end, message; idle and session_start on request. Adding again for the same terminal changes its events. At most 8 per agent. `harness_listener_remove` (w) and `harness_listener_list` (r).
- The backend runs one follower per agent and computer (`harness_follow.py` through the controller's monitor stream; the computer cannot reach the backend), restarted with `--since` the newest delivered line whenever that agent's listeners there change, so nothing is lost. Lines within 200 ms are one wake-up, held (merged) while the agent handles the previous one and then waiting out another 200 ms window; at most 10 events are shown per wake-up, each naming its harness, and at most 50 are kept (older ones only counted). The backend enforces `notify_supervisor`'s limits again per listener (one `message` per 10 s, 30 an hour, by its own clock; the guest is untrusted): excess messages are dropped and counted in the next wake-up. Followers record the terminals they cover, which is how `notify_supervisor` knows someone listens.
- A listener ends, and the agent is told, when its session ends (exit, logout; not `/clear` or resume), the computer is no longer assigned, the follower cannot run (an older image: update it), or the connection ends. A backend restart stops listeners and tells their agents (rows in `ComputerWatch`, kind `harness-listener`); the harness keeps running.
- `watch_terminal` on a terminal whose program is `claude`, `codex`, `opencode` or `pi` adds a hint pointing to a listener; Knowledge cues point to `practices/harnesses`. Event text is computer output, labelled as data, never the human's instructions.

## Images and private sessions

Tools return real model image-content blocks plus text metadata. Known vision models retain their input capability; unknown/text-only models are rejected for screenshots, not fed base64 as text. Fresh images are captured/cropped inside the guest, not enlarged from a card thumbnail. JPEG quality is 85 with a 2 MiB compressed-image bound and source dimensions up to 4096 per axis / 16 million pixels.

Screenshot copies share an app-local **50,000,000-byte disk pool** at `.local/computer-screenshots/`. When the threshold is reached, evict at least **10,000,000 oldest bytes** (more if needed for the incoming image). Text activity/reference metadata remains; expired copies show unavailable rather than inventing a reconstruction. Private Pi checkpoints store references without duplicate base64, and rehydrate available images on the next run; missing images remain metadata with a fresh-look reminder. No historical screenshot renews action allowance. Exclude this cache from backups if oldest-first eviction must remove older copies; external model providers have their own retention policies.

## Swarm Knowledge and model guidance

Swarm Knowledge splits the guidance into concepts (`concepts/computers`, `/desktop`, `/terminals`, `/files`, `/watches`) and practices (`practices/computer-use`, `practices/desktop`, `practices/browser`, `practices/terminals`, `practices/files`, `practices/waiting`, `practices/harnesses`), linked to each other; see [Swarm Knowledge](swarm-knowledge.md). Entries include examples, coordinates, limits, ownership, human help and recovery. Content is reference, not a grant or higher-priority instruction. Hard execution rules do not rely on model compliance.

Browser guidance requested by the owner:
- Report a blocking CAPTCHA through an authorized channel **before** one default attempt. Immediately report its outcome; further attempts require human approval. No reload/solver/identity rotation to disguise retries. This is guidance, not a deterministic visual CAPTCHA detector.
- On observing the human's Google account signed into Chrome, warn about possible automation-related account/IP restrictions; wait for informed human permission before Google services. Use a non-Google route such as DuckDuckGo meanwhile. Do not assert a guaranteed ban or silently change/logout the account.
- That Google-specific gate does not automatically apply to GitHub/other accounts: assess task/account risk, warn as appropriate and proceed reasonably within existing instructions/grants.

## Rollout boundary

Controller, backend and guest runtime scripts all change. Existing desktops do not gain the guest scripts through a backend/frontend deployment alone. Build/test with disposable images first, retain live IDs/volumes and do not silently restart the owner's desktop. See [Computers](computers.md) and [development](development.md) for isolation and deployment gates. Durable operator activity is separate from chat and private session context; its own migration/API is integrated alongside this feature.

The rollout passed 307 TypeScript tests, 11 guest Python tests, 25 focused browser checks, typechecks/build, feature CI, and isolated production migrations/API and real X11/GTK screenshot/Unicode/cancellation checks. After an idle-run preflight and protected app-data backup, the three guest helpers were installed in-place through `docker exec`/tar (Docker cp cannot see this Sysbox guest's `/opt/swarm` mount view). Only backend/frontend/controller containers were recreated; the owner's desktop container, image ID, start time, volumes and running session were unchanged. Future computers use the tested helper-overlay image under the existing H.265 tag. Live read-only capture returned 634×356 from 1920×1080 with no input sent; HTTP19090 and certificate-validated HTTPS19091 remained loopback/Tailnet TCP-only. Existing agent/message/computer/private-session counts were preserved. No real-model desktop action or live desktop input was performed for validation.

## Knowledge first

The system prompt requires an agent to read `concepts/computers` and `practices/computer-use`, plus the concept and practice for each surface it will use (desktop, terminals, files, waiting), with `read_knowledge` before calling `use_computer` or any other computer tool whenever those entries are not in its retained context (a new or compacted conversation), and the `use_computer` claim result repeats the reminder. Old IDs such as `swarm/computers/use` still resolve.

## Recording

`start_recording({sources, mode, computer?, to?, fps?, events?, hide_typed?, audio?, keep_start?, keep_end?})`, `renew_recording({events?, keep_start?, keep_end?})`, `mark_clip({label?, before?, after?})`, `stop_recording({id?})` and `recording_events({match?, source?})` record a computer the agent can read (no claim needed; a holder is told). Sources are `"desktop"` and/or `{terminal: <session ID>}`, at most 3 per agent and per computer.

- **Inside the computer** (`templates/default/runtime/recording.py`, run by the controller's `POST /computers/:id/recording/{start,mark,update,stop,list,terminals}` as `agent`): a desktop source is `ffmpeg` x11grab of `:1` plus the PipeWire `swarm-output.monitor` sound, `h264_vaapi` on the render node with the colour conversion on the GPU too (`hwupload,scale_vaapi=format=nv12`; measured 2026-10-01 on a Radeon 680M at about 17% of one core at 30 or 60 fps, against ~107% at 60 fps converting on the CPU; `libx264` fallback), VBR capped at the Settings bitrate, in 2 s MPEG-TS segments under `/tmp/agent-recordings/<id>/`. A terminal source samples `tmux capture-pane -e` at its frame rate (changed screens only) and keeps an asciicast via `pipe-pane`; on save the screens are drawn with Pillow (DejaVu Sans Mono, the dashboard terminal palette) and encoded with `libx264`.
- **Events**: `computer-use.py` and `computer-terminal.py` append each action's type, start and end time (and its text, key or point) to `/run/user/1000/swarm-recordings/{desktop,terminal-<session>}.events` only while a recording of that kind is active, so desktop recordings see only desktop actions and a terminal recording only actions typed into that terminal; marks are kept per recording. Tools carry a second label besides r/w/rw for this (`run_actions`: desktop recording events; `terminal_run_actions`: terminal recording events; `help` shows it); no other tool produces events. In events mode, segments no clip can need are deleted as the recording runs; on stop the clips (each event padded by its rule, from the action's start to its end, overlapping or touching clips merged) are cut and re-encoded.
- **Cutting clips** (`plan_clips` in `recording.py`): each event keeps `[start − before, end + after]` (from the action's start to its end). Padding, first match wins: a mark's own `before`/`after` (`mark_clip({label, before?, after?})`, 0–30 s, that mark only; it is clipped even with no `mark` rule), the rule for its type in `events`, then `*`, then Settings → Swarm's default padding (0.5 s each side). Listed `events` clip nothing else. Clips that overlap or are under 1 s apart merge. `keep_start` stretches the first clip back to the start of the recording and `keep_end` the last one on to its end (both with no events: the whole recording); the rolling buffer then keeps everything before the first event, or after the latest clip, until stop. `renew_recording({events?, keep_start?, keep_end?})` changes them for the rest of the recording (each source keeps its own kinds of events). `events.log` records "start kept"/"end kept", each event's clip and time in it, a mark's own padding, and "(no clip)" for events outside every clip.
- **Saved** to `~/Videos/agent-recordings/<UTC time>_<agent>/` on that computer (Keep storage): `clip-NN-desktop.mp4`, `clip-NN-terminal-<name>.mp4` (+ `.cast`), numbered per source, and one shared `events.log` (UTC time, time into the recording, source, file and time in it, action; typed text unless `hide_typed`). `stop_recording` returns the files and one contact sheet of stills (kept in the screenshot pool like other tool images).
- **Lease** (`backend/src/computer-use/recordings.ts`): Settings → Swarm `Recording stops unless renewed after` (default 300 s), a reminder at `Recording renewal reminder after` (150 s), `Longest recording` (30 min), bitrate (1000 kbps max), frame rates (desktop 30, max 60; terminal 15, max 30) and default padding (0.5 s each side). Reminders and automatic stops wake the agent with a platform computer event. Turning the computer off saves first; removing the assignment stops and saves; deleting the computer ends it unsaved; a backend restart saves it from the `AgentRecording` row and leaves a next-turn notice. The recorder also stops itself a minute after the longest recording if the backend is gone.
- **Dashboard**: a red "Recording · <agent>" status with **Stop recording** in the viewer header (`POST /api/computers/:id/recordings/stop`; saved, agent told) and a red **Rec** badge on the computer's card (`recordings` in `GET /api/computers/control`).
