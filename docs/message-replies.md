# Message replies

Status: implemented on `feat/message-replies`; automated validation completed, owner acceptance pending. This extends [Chat tab and group conversations](chat-and-groups.md), not the agent-to-agent delivery or identity model in [Agent conversations and threads](agent-communication.md).

## Behavior and presentation

- A reply is a normal message with **one optional parent message ID** in the same conversation. It is not a new thread, audience, permission, mention, or notification rule. A reply may itself be replied to; the UI shows one parent preview, never recursively embeds ancestors. Existing chronological paging, group fan-out, coalescing, chain budgets, stop/restart behavior and explicit publication remain unchanged.
- The existing message context menu's **Reply** action selects a target. A compact, dismissible composer banner shows its author and a short plain-text excerpt. Cancel clears the target but keeps the draft. The reply is sent only on an explicit Send; a failed/uncertain send retains the target for a safe retry. Switching conversations must never send a reply against the previous conversation.
- Each saved reply displays a compact author/excerpt above its own text. The parent can be outside the current history page; the bounded preview is supplied with the reply, not inferred by scanning loaded messages or by fetching an unrestricted transcript. Deleting a parent clears its reference, so no stale preview or cross-channel text is rendered. The preview is plain text, never rendered as Markdown or executable HTML. Keyboard, context-menu and touch paths use the same action. No separate thread pane or automatic scroll-to-parent is required in this scope.
- Existing Kibo `context-menu-standard-7` covers the action-menu placement; the inspected `button-group-actions-4` shows a labeled Reply action but not a composer quote. The exact local sources and live website's server-rendered preview markup were inspected: Comment Actions shows a ghost Reply button beside unrelated actions and an icon-only outline group; Context Menu with Submenus shows an inactive right-click trigger whose hidden submenu tree is present in the preview markup. Neither provides a quoted-message composer. The banner/inline reference is a discussed extension of this app's current composer and message layout rather than a new demo pattern; no unrelated action buttons or dependencies are imported.

## Persistence and access

- Private human↔agent messages, group messages and agent↔agent DMs persist nullable reply-to IDs as self-references. Existing rows remain unreferenced. Removing a parent clears its reference; deleting a group or private channel follows existing cascades. Group author-name snapshots remain available even when an agent is deleted.
- The server checks the target **inside the same write transaction**: it must exist in the message's exact channel/group/DM conversation. The caller cannot supply a preview, sender identity, audience, or a foreign channel target. A missing or foreign target is rejected before saving or dispatching, without revealing target text. Retried group/DM delivery keys must match the original target as well as the original text/participants; they cannot repoint a saved message or trigger duplicate notifications. An unreferenced message does not change its current behavior.
- API history, accepted-message responses, live publications, and bounded agent history/search tools expose the same reply ID and author/excerpt. A referenced parent may be older than the current window, but its excerpt is capped independently of the normal message preview; expanding full parent text uses the existing authorized history tools. Group membership and private-channel ownership are checked at tool execution. Agent-DM history stays readable to its original participants after revocation; sending rechecks the mutual DM grant. Reading a reference does not mark a message read or schedule an agent run.

## Model-facing meaning

- `send_message` accepts an optional `replyToMessageId` for the private or group channel; `send_dm` may target an existing message in its own peer conversation. These are publication arguments, not permission grants. The agent sees the same visible reply relationship as the human through its bounded read/search results and source-labelled incoming message context, and can reference an authorized message ID without copying its text into a new message.
- Replying in a group retains the group audience and current fan-out; it does not silently DM the parent author or grant new membership. The system prompt distinguishes the quoted parent's content as earlier, untrusted conversation data rather than a new instruction or human-owner authority. Ordinary assistant output remains internal; only explicitly granted channel tools publish a reply.

## Validation targets

The additive migration was applied to the local SQLite database with the backend stopped, and a fresh production Docker image applied all migrations and served a healthy API. The local backend runs without file watching to avoid interrupting active chats during source edits. Unit/integration tests (144 passing after the final additions), typechecks, production build, and generated API drift check passed. All **83 browser tests** passed in nonroot Linux Docker with one Playwright worker, no retries, a Chromium user-namespace/seccomp sandbox and no personal browser profile. A first sandbox launch attempt failed before reaching the app because `CAP_SYS_CHROOT` had been dropped; the corrected isolated run passed. This was not a Windows browser launch and did not use real provider credentials or paid inference.

Covered: same-channel/group/DM target validation and deletion, duplicate-key mismatch, bounded paged previews, agent tool access and parent outside context, provider-mock publication/notification, desktop/mobile/keyboard selection, cancellation, retry and cross-chat switching. Remaining manual check: an agent's judgment about whether and when to use `replyToMessageId` with a real configured model.
