# Computers — lifecycle, previews and interactive desktop

Status: computers (lifecycle, low-rate previews, interactive desktop, file browser, terminals and agent use) are deployed to the trusted Tailnet dashboard. Allowed Tailnet peers control the desktop directly; there is no app login or second GNOME grant. Dated rollout notes, benchmarks and superseded trials are in [history](history.md).

The feature set includes [agent computer use](agent-computer-use.md): explicit per-agent assignments, single-agent claims, screenshot/action-combo tools and human Force release. The human viewer defaults to Input locked, with an explicit Input live toggle that does not revoke an agent's claim.

## Terms and ownership

A **computer** is a persistent, shared Ubuntu GNOME environment, independent of agents and chat channels. No agent is assigned to or given tools for one by creating it. Its stable UUID, operator-chosen name, create-idempotency key and lifecycle state are saved in the platform's existing Prisma/SQLite database. Docker containers, named home/workspace volumes and a private network carry matching managed-resource labels. Docker is observed runtime state, not a replacement for the platform identity record.

**Create** reserves the identity first and uses its UUID for fixed Docker resource names. The dialog prefills a disposable default name, `Workspace-NG` plus four random uppercase letters, chosen against the visible roster so it does not repeat a current name; the owner may edit it freely. The backend is authoritative: it rejects a name that matches an existing computer case-insensitively, so exact-name delete confirmation cannot become ambiguous. Repeating the same request key/name reuses that identity; a different name with the key is rejected. If provisioning fails, keep an operator-visible failed record and any owned partial resources; do not automatically delete possible user files. A GET after a backend crash reconciles a still-creating record with a running owned container, or marks it failed after the create deadline so it can be deleted by exact name. At most 100 platform computer records may be retained; existing idempotency keys still work at that cap. **Delete** requires the exact saved name at the API, checks Docker labels before touching any resource, then permanently removes the computer container, its own home/workspace volumes, egress sidecar and private network. A failed midway deletion remains retryable. It cannot remove an agent, chat, foreign container or unlabelled volume by supplying a name.

## Execution and isolation

The browser reaches one dashboard origin/port. Caddy/Vite forwards `/api` to the backend; the backend alone talks to an internal **computer controller**. Only that narrow controller mounts the root-equivalent Docker socket, without `.local` app data or provider credentials. The browser cannot choose an image, host mount, device, network flag or Docker API URL. Computers publish no per-computer host ports.

A computer runs with `sysbox-runc`, a user namespace, Docker's Chromium-compatible seccomp profile, CPU/memory/PID limits and only two owned named volumes. Its guest image has Pi CLI, uv, nvm, gcc/g++ and ffmpeg available to a human terminal, with **no developer credentials or agent computer grant**; installing a program is not an authorization to run it as a product agent. The non-root `agent` user (uid/gid 1000, home `/home/agent`) has **passwordless sudo inside the computer**; no Docker socket, host namespace, host cgroup bind, privileged mode or host filesystem mount is granted. The uid is unchanged from the earlier `ubuntu` account so an existing home volume stays readable when mounted at `/home/agent`. Deployed 2026-09-26 with the generated-name default: the live controller creates every computer from `agent-swarm-default:http-jpeg-xorg120` (`e97a1e66…`) with this account, and the previous `ubuntu`-era Workspace was deleted by its owner beforehand, so no guest still runs the old name. `no-new-privileges` is intentionally not set on that sudo-capable computer because it would block setuid sudo. On the development host, Sysbox mapped computer UID 0 to unprivileged host UID 165536 and Chrome reported PID/network namespace and Seccomp-BPF sandboxing. This is observed host-specific behavior, not a universal claim that container root cannot exploit the kernel. If Sysbox is unavailable, creation must fail rather than fall back to privileged runc.

**Guest hostname.** The desktop's hostname is derived from its operator-visible computer name rather than left as Docker's default (the container's short ID), so the guest shell prompt reads `agent@workspace-ngclzr` instead of `agent@bea473f5a9f4`. `computerHostname()` lowercases, collapses every non-alphanumeric run to a single hyphen, trims hyphens, and caps at 63 characters to stay inside RFC 1123; a name with no usable characters falls back to `computer-<id prefix>`. Two different names can slug to the same hostname (for example `Desk One` and `Desk-One`), which is cosmetic only: each computer owns its bridge and the media relay is addressed by a UUID-derived alias, never by hostname. Note the Docker API trap — `Hostname` belongs in the create body's **top-level Config**; placed inside `HostConfig` it is silently ignored and the container keeps its ID.

**Desktop workspaces and dock.** A Windows Win+Tab *virtual desktop* corresponds to a GNOME **workspace inside one Computer**, not another Computer or the persistent `/workspace` folder. New guest images configure one fixed GNOME workspace (dynamic workspaces off, count one). Ubuntu Dock favorites are Files, Google Chrome and Visual Studio Code, in that order; Trash is the dock's separate icon and stays enabled. Chrome retains the X11 GPU-grant-aware desktop launcher. VS Code was already installed from its signed vendor apt repository, so this change pins its existing `com.microsoft.VSCode.desktop` entry rather than adding another editor. These are guest UI preferences, not a host resource limit or a security boundary against the guest's sudo-capable user. The then-running owner desktop's preferences were changed in place through **its actual GNOME session bus**, after checking that no windows occupied another workspace: X11 advertised one desktop, the favorites and Trash setting matched, and its original container/image, named volumes and running processes were not restarted or replaced. Future new computers get these schema defaults; merely updating an image never overwrites an existing home volume's customized preferences.

**Guest clock.** A computer never inherits the host timezone: the operator sets `COMPUTER_TIMEZONE` to an IANA zone name (for example `America/Toronto`) and the controller passes it to each new desktop as both `TZ` and `COMPUTER_TIMEZONE`, which the root bootstrap resolves to `/etc/localtime` and `/etc/timezone`. Validation accepts only plain zone path segments, and the bootstrap links a zone only when that `zoneinfo` file exists, so a bad value leaves the image default rather than pointing at host files. Empty leaves computers at UTC. Changing the operator default affects newly created computers; an existing desktop keeps its saved timezone until Settings explicitly replaces its **stopped** container with new TZ environment, preserving named volumes. A manual `/etc/localtime` relink alone is not durable because existing processes and future restarts retain the old TZ environment. Dashboard timestamps are browser-local and unaffected.

Each computer connects only to its own Docker bridge with `gateway_mode_ipv4=isolated`: Docker does not assign that bridge a host gateway address. A separate small **egress sidecar** sits outside the sudo-capable computer namespace, connects that private bridge to a shared public-egress bridge and filters forwarding before NAT. It permits public internet/DNS for browsers, apt and development; it rejects private/host/Docker/Tailnet/link-local destinations. Container root can change routes inside its namespace but cannot alter the gateway's firewall. The gateway must be filtered before the computer is started. Both workloads use no automatic Docker restart policy; **controller startup** recovery starts/validates egress before starting a stopped desktop, avoiding an unfiltered gateway start during host reboot. This is not continuous crash/OOM monitoring. A normal Docker `--internal` bridge alone is **not sufficient**: a disposable probe reached its host gateway. The specific isolated-gateway + sidecar design passed public-web and deliberately reachable private-target probes, including gateway reject counters and an attempted root route change. Network and kernel isolation still require ongoing validation on each deployment host.

### Resource limits and OOM

Each desktop is created with operator-selected Docker CPU and RAM quotas (`NanoCpus` and `HostConfig.Memory`; current defaults four core-equivalents and **4 GiB RAM**) and a PID limit of 1024. CPU quota does not pin the guest to specific physical cores. The create dialog now exposes per-computer CPU and RAM choices. Its bounds derive from Docker-host logical CPUs and installed RAM but are policy-capped at **8 cores / 16 GiB**, with the current operator defaults **4 cores / 4 GiB / America/Toronto** on this host. The controller revalidates every choice where Docker executes it; saved Prisma fields are nullable for older computers rather than falsely backfilled. New and edited computers explicitly set `MemorySwap` to **twice the selected RAM**, retaining an equal-size host swap allowance. On the tested host a 4-GiB RAM choice therefore gives **4 GiB swap** (`HostConfig.MemorySwap=8 GiB` total); the guest cgroup reports `memory.max=4 GiB` and `memory.swap.max=4 GiB`. The card's Memory dial uses the inspected **4 GiB RAM** limit, not RAM plus swap or Sysbox's misleading host-sized `memory_stats.limit`. Host swap belongs to the host, **not** the guest's persistent home/workspace volumes: this host prioritizes compressed-RAM `/dev/zram0`, then can use NVMe-backed `/swap.img` and `/swap2.img` if needed. Swap can slow the desktop and is not equivalent to more RAM. These backing devices and Docker's inferred swap default are host-specific; verify them on another installation.

Two bounded probes used a **disposable Sysbox container** with the same 4-GiB RAM, 4-GiB swap, four-CPU quota and `RestartPolicy=no`, never the owner's desktop. Touching **5 GiB** completed normally, with ~1.18 GiB peak swap and no OOM. A **9-GiB target** logged 7,936 MiB before the allocator was OOM-killed (exit 137); RAM and swap each peaked at 4 GiB and the cgroup recorded `oom=1`, `oom_kill=1`, `oom_group_kill=0`. Its harmless PID 1 survived: the container remained running with `RestartCount=0` and `ExitCode=0`, **even though Docker's `State.OOMKilled` became true**. That flag alone does not establish that the whole container stopped. The kernel can choose a different victim under different workloads: losing Chrome may leave the desktop up, losing a critical desktop process may break its session, and losing PID 1 stops the container. Docker will not automatically restart it (`restart=no`); controller **startup** reconciliation can separately restart a stopped owned desktop, but the running controller does not monitor and restart OOM exits. Both probes removed their own containers, left no test resources, and do not prove behavior under host-wide pressure.

## Preview, status and limits

The Ubuntu GNOME 46 image boots a 1920×1080 headless Wayland virtual monitor and user PipeWire session. GNOME's direct Screenshot D-Bus interface refused external capture; the runtime instead keeps a Mutter ScreenCast `RecordMonitor` session alive and receives its PipeWire node. On demand, a bounded GStreamer PipeWire/JPEG pipeline produces a 480×270 image. Mutter's private API and its BGRA 1920×1080, variable 0/1 frame-rate caps are tied to the Ubuntu image version and need regression checks on upgrades. No interactive WebSocket/video session is opened for a grid card; the stage-2 Selkies listener inside a computer remains idle until a viewer connects. The browser requests thumbnails every 500 ms per visible, running card and stops when the card/tab is hidden; the controller coalesces concurrent preview requests and caches thumbnails for 400 ms measured from capture start (so a 500 ms poll can produce a fresh frame). Full-size consent previews keep their separate 1.8-second cache. Requests are a target cadence, not guaranteed new visual content if the guest does not change or capture falls behind. In the isolated dev run, two independent computers returned real JPEG previews concurrently in about 0.22 seconds total (14,431 bytes each); this is a small-sample feasibility measurement, not a production latency/scale guarantee. A missing/stopped preview is indicated instead of presenting an old frame as live. The controller also reads bounded Docker CPU and memory statistics; transient stats failures yield unavailable values, not invented zeroes. If the controller itself is down, the API still lists saved platform computer identities with an unavailable state while disabling destructive/create actions; a disconnected backend must not make the computers appear deleted.

The UI keeps the existing Kibo-derived Basic Tabs navigation and typed Delete Confirmation dialog. Each card shows its name with a right-aligned **`...` actions trigger** and two circular usage dials — CPU at the left edge, Memory starting at the card's centre — with no inline power button. The same Radix context menu opens from the trigger and from a right click on the card (the trigger dispatches a synthetic `contextmenu` event, the dashboard's existing pattern): Open, Power off/Power on, File browser (enabled for running computers), Settings, a separator, a "Danger zone" label and a red Remove. Right-clicking empty space on the page (or the page with no computers) instead offers page actions: **New computer** and **Refresh**. Settings opens a URL-addressable dialog: CPU and RAM update live through Docker's owned-container update API (reducing RAM below current use may OOM-kill processes), while timezone changes require an explicit **Power off → confirm stopped-container replacement → Power on** sequence. The controller preserves the same UUID, approved image, private network and named home/workspace volumes, prepares a replacement before retiring the old stopped container, and attempts rollback on failure; no active desktop is restarted silently. A disposable Sysbox computer verified the live CPU/RAM cgroup update, a timezone change to UTC after power-off, persistent home sentinel, and successful power-on. The ellipsis trigger is transparent at rest and reveals a muted surface/border on hover or keyboard focus. Delete therefore lives only in the menu, which keeps exact-name confirmation unambiguous now that names are unique. Power control is real: `POST /api/computers/:id/power` records the operator's intent in `Computer.desiredState` **before** asking the controller, stop tears the media relay down before the desktop while leaving the filtered gateway, bridge, both volumes and the record intact, and start refuses when the render-device grant no longer matches, bringing the gateway up before the desktop reattaches. Because the controller's own boot reconciliation starts every owned desktop it finds, the backend re-applies recorded power-offs at startup (`reconcileStoppedComputers`); failures are logged, never thrown, so a controller outage still boots the dashboard. Card thumbnails **request** at 2 fps (and receive fresh captures at that rate when the guest/capture keeps up) and dissolve: at most two layers exist, the previous frame stays a **fully opaque floor**, and the newest frame alone ramps its opacity 0 to 1 over it before being promoted. A sum-to-one crossfade was tried first and rejected — with both layers semi-transparent over the card's black backdrop the composite is `t*new + (1-t)^2*old`, which dips ~23% in brightness halfway through every blend and reads as a breathing light at 2 fps (measured, and now asserted by a browser test that dissolves two identical-luminance frames and requires the dip to stay under 3%). Reduced motion snaps instead of dissolving. Thumbnails stay 480×270 (worst-case 94 KB against the 192 KiB thumb cap; 854×480 measured 255 KB on photographic desktops). Opening a computer hides the global tabs to give its viewer the full available height; the **Computers / Computer Name** breadcrumb remains and returns to the grid, restoring keyboard focus to the Computers tab. The desktop fits the browser width rather than panning unnecessarily on large screens, while narrow phones retain horizontal pan. The pinned client marks its JPEG canvases **and** its WebCodecs `<video>` sink `crisp-edges` even when its fixed 1920×1080 desktop is shown smaller; the trusted viewer frame overrides all three to browser-smooth interpolation, because nearest-neighbour downscaling of a 1920×1080 desktop reads as pixelation (measured: 0.02% intermediate greys versus 50.02% when smoothed). The viewer sizes its iframe box to the exact 16:9 **contain** fit of the available area and recomputes it from a container `ResizeObserver`, so resizing the browser window re-fits instantly: the guest resolution is operator-locked, so nothing is asked of the desktop and no reload is needed. Phone viewports keep the deliberate full-width pan. This is frontend-only presentation: it leaves source resolution, JPEG quality, input mapping, pinned executable bytes and the guest untouched. Smoothing removes forced nearest-neighbor pixel edges but cannot recover details lost to JPEG compression or downscaling. Dashboard routing and viewer scaling never change the guest display: the X11 runtime fixes **1920×1080**, Selkies has resize disabled, and the deployed Mutter logical monitor and text scale both report **1.0**. A viewer-requested larger size is ignored by the server. The frontend-only route and canvas changes do not alter the guest. An audit of the **former** X11 server found it separately accepted a browser's `scaling_dpi` even with resize disabled: `Xft.dpi` changed 96→192→96 across viewers. The replacement X11 image now applies the operator-owned `--scaling-dpi=96` override. A disposable and subsequently a **live** DPR-2 primary browser proposed DPI192; Selkies rejected it against `['96']`. The live guest's Xft resources stayed **unset before and after** DPR-1 and DPR-2 sessions, and GNOME logical/text scale remained 1.0 at 1920×1080. Unset is not an explicit `Xft.dpi=96` claim; the test proves no browser mutation. The Kibo Image Card preview/source placed its title before the image, conflicting with the owner's chosen screenshot-first YouTube-like grid; that card composition is intentionally custom and retains the requested image → name → CPU/memory hierarchy without demo data or dependencies.

The lifecycle/preview milestone did not include agent assignment, console/tmux access, real-time input, clipboard/audio, multi-user login or interactive video. Current access policy is the trusted dashboard network: anyone allowed to open it may manage computers; **do not expose it publicly**. App-level user control is later scope.

The desktop viewer identifies its agent control holder with that agent's configured animated avatar and “Name is on this computer.” Its Working/Typing/Ready indicator reuses the dashboard's existing run event state, not a new event stream or endpoint-health probe; unavailable state is labelled rather than guessed. Avatar lookup also supports a holder outside the loaded roster page. Force release and the independent human-input toggle retain their existing behavior.

**Audio.** Computers have no sound card. The desktop session starts PipeWire, then (once its socket exists) WirePlumber and `pipewire-pulse`, and PipeWire always provides a **Virtual speakers** output (`/etc/pipewire/pipewire.conf.d/60-swarm-output.conf`). WirePlumber's Bluetooth monitor is disabled (`/etc/wireplumber/bluetooth.lua.d/80-swarm-no-bluetooth.lua`) because it loads a logind plugin that cannot start in a container and took WirePlumber down with it. Without an audio output, Chrome's media pipeline stalled before the first video frame, so YouTube never played. The viewer can stream that output: Selkies runs with audio enabled but **capture stopped until requested** (`--audio-on-start=false`, no microphone, capturing `swarm-output.monitor`). The viewer's **Sound** toggle is off every time the viewer opens (and in the Terminal view); turning it on starts Opus capture and playback, turning it off stops capture. Browsers decode this audio only on secure pages, so on the plain-HTTP dashboard address the toggle is unavailable and says sound needs the HTTPS address. Running desktops pick up the new Selkies flags on their next power cycle.

## Persistent terminals

A running computer's card menu also offers **Terminals**: shared guest tmux sessions with a real xterm.js PTY view (120×36 by default; rename and window size from a session's right-click menu), direct keyboard (never mouse) input, a session list beside a centered console window, a key bar for browser-reserved keys (sent over the live stream) and a popup Cancel/Delete confirmation. The desktop viewer's header has a **Desktop / Terminal** switch beside the computer name (icons only on phones); the address records it (`/computers/:id` or `/computers/:id/terminal/:session`), so a refresh or shared link returns to the same view and session that shows the same terminal workspace in place of the desktop (the stream stays connected, and desktop-only controls hide while Terminal is shown). A **‹** handle on the desktop's right edge (**‹ Terminals** on hover) opens a **Terminals** drawer listing the computer's sessions with their current screens rendered as text (read one after another, since the computer admits one operation at a time). Its **+** (and the empty drawer's **New terminal**) opens the same New terminal form as the Terminal view; the new terminal floats up at once. Choosing one brings it up as a floating window over the live desktop that keeps the terminal's own shape (resizing follows the width; the height always wraps the grid), is dragged by its title bar and stays inside the viewer; its single yellow traffic light minimizes it back into the drawer. New terminals are created from the Terminal view. The desktop stays usable wherever the window does not cover it. With a mouse, both edge handles stay invisible until the pointer comes near (about 180px shows just the glyph, about 90px its round button) and unfold their label on hover or focus; touch screens always show the labelled pill. When an agent holds the computer, clicking it in the header opens a floating chat with that agent over the desktop (the same conversation and draft as in Chat, the latest 80 messages, styled and moved like the floating terminal; **Open in Chat** shows the whole conversation). The chat window grows out of the header agent and shrinks back into it; the terminal window grows out of and shrinks back into the right edge. Both floating windows can be dragged anywhere on the page, even past the viewer, but keep at least 64px on screen. The window touched last is on top and focused (brighter edge, deeper shadow, yellow light); touching anything else leaves neither focused (grey light). A small **^** handle at the bottom of the viewer expands to **All computers** on hover and opens a bottom drawer of computer previews for switching desktops without leaving the viewer. Closing the view or releasing agent control leaves programs running; power-off ends them. This is separate from the read-only file browser and synchronous core `bash`. See [terminal tools, operator API, lifetime and safety](persistent-terminals.md).

## Operator file browser

Choose **File browser** from a running computer's card menu. A centered Kibo `dialog-standard-3`-derived modal keeps navigation and footer fixed while its contents scroll. The browser starts in `/workspace`, where agents work; the home folder is one path edit away. Listing and previewing wait briefly for each other instead of failing. Clickable path breadcrumbs use the same shared bordered style as Settings → Swarm Knowledge; an editable path and a case-insensitive folder-name filter remain available. There are no Back/Forward/Up/Refresh buttons, quick-access sidebar or locations dropdown; the file list uses the full width. Click an ancestor breadcrumb to move up, open a folder to move down, or click the current folder breadcrumb to leave a file preview. Narrow screens put size/date beneath filenames.

This first slice is **read-only**: browse folders, preview text and download individual files. Upload design is deferred; no create/rename/delete/edit or directory ZIP controls are exposed. A file's download button and its preview both offer download. Text previews are capped at 64 KiB and label truncation; binary files are download-only. Downloads are capped at 64 MiB, served as `application/octet-stream` attachments with safe filenames, `nosniff` and `no-store`. Preview text is inert, never guest-supplied HTML. Listings have 200-entry pages, scan at most 20,000 directory entries, and explicitly report incomplete scans/omitted undecodable filenames. Filtering is within that scan, not recursive search. Directory contents are not snapshots: concurrent guest changes can shift pages; refresh when necessary.

These are human operator APIs (`GET /api/computers/:id/files`, `/file-preview`, `/download`), **not new agent tools or permission grants**. They neither require nor acquire/release an agent claim. Existing trusted-dashboard access permits these operations; the dashboard must not be exposed publicly. The backend checks the saved running state, and the controller checks managed ownership and the actual running instance before executing a fixed read-only Python operation as guest uid/gid 1000. Paths never select a platform-host file. Symlinks (including symlink path components), virtual filesystems and non-regular downloads are unsupported; use canonical directories such as `/usr/bin` instead of `/bin`. Descriptor-based path walking prevents symlink replacement races. File permissions still apply; sudo is not used. The computer and agent can continue operating concurrently.

File operations have time/byte limits and one operation per computer, two globally. Downloads are buffered, not end-to-end streaming; peak memory includes bounded buffer copies. Closing the modal aborts its browser requests but does not stop the computer or agent. The guest reader is supplied directly as trusted argv: deployment updates backend/controller/frontend only, with no guest helper installation, image upgrade or desktop restart. A sudo-capable guest can replace its own executables; this is not an adversarial-guest trust boundary. Built-in Selkies file APIs remain denied by the existing proxy allowlist.

## Interactive runtime (isolated E2E verified; Tailnet HTTP/JPEG deployed)

The stage-2 image pins the MPL-2.0 Selkies 2.0.0 Ubuntu 24.04 packages by amd64/arm64 SHA-256. **Selkies** supplies H.264 encoding, WebSocket transport, WebCodecs browser decode and mouse/keyboard input; WebRTC/TURN is intentionally not enabled because it would require additional relay TCP ports or a non-HTTP multiplexer. This stream is distinct from the sparse JPEG previews. It starts inside each managed GNOME computer, not in the backend's chat event loop, and does not publish a host port. GNOME's first-run RemoteDesktop portal needs explicit screen-sharing and remote-interaction consent. The portal's persistent restore token belongs to the computer's home volume, not the dashboard or any agent. Because headless GNOME has no session manager linking private video ports, the in-computer bridge identifies its own preview PipeWire node and links only the one other matching GNOME video output to Selkies's matching input; ambiguous capture sets fail closed. No Docker socket enters the computer. By default it also receives no host device; an operator may explicitly opt in to sharing only a validated `/dev/dri/renderDNNN` node through `COMPUTER_RENDER_DEVICE` for VA-API encoding. This shares the host GPU driver/kernel ioctl surface with a sudo-capable computer and is therefore a real additional trust decision, not an isolation guarantee. Card/modeset devices and arbitrary paths are rejected. This operator setting is checked against the actual device mapping on controller restart; if it changes for an existing computer, the controller **stops that desktop without deleting its home/workspace volumes** rather than silently retaining a revoked GPU grant. Restore the prior setting and restart the controller to re-open it, or arrange an explicit migration of that owned computer; changing Docker's existing device mount in place is not supported. The image has Mesa VA drivers and `vainfo`; without a render node Selkies falls back to software x264. Do not grant the whole `/dev/dri` directory or relax the browser seccomp profile to make GPU encoding work. A small, non-root **media relay** per computer copies encrypted TCP bytes from a shared, gateway-less Compose media bridge to **only that computer's private IP**. It has no Docker socket, host mounts, capabilities, writable root filesystem or published port. Its listener binds the address selected from the validated media subnet (interface numbering is not a security boundary); the computer cannot connect to either the media address or the relay's private address. The controller verifies its Docker ownership/alias and removes it before removing the computer. The namespaced Docker resource name can exceed DNS's 63-byte label limit, so Caddy dials a canonical `computer-<UUID>` alias scoped to that media bridge. Exact UUID-path routing and WebSocket proxying share the **sole external Caddy port** with the dashboard and API; interactive video packets never enter the backend chat event loop (the separate bounded consent JPEG does). A separate dev Caddy uses the same route snippet in front of Vite on loopback:5173. Caddy forwards the dashboard Host header for Selkies' same-origin WebSocket check and accepts only the computer's internal self-signed TLS on this isolated upstream. The H.264/WebCodecs path still requires a trusted HTTPS origin **on the same port** outside localhost. The deployed Tailnet HTTP/JPEG path below avoids WebCodecs without changing browser security flags; private-LAN HTTP is also available as an opt-in overlay.

For the original Wayland/portal mode (not the deployed X11 viewer), a **full-resolution, bounded, on-demand JPEG** uses the same private Mutter/PipeWire session as the small grid preview, but has a separate short cache and a 512 KiB image limit. A person viewing that computer can send a normalized one-click position; the backend checks the saved running computer, and the controller rechecks ownership/running state and coordinates where it executes a short-lived, non-root Mutter RemoteDesktop D-Bus session **inside only that computer**. No agent tool, host input device, raw command, automatic blind coordinate click, or separate computer port is introduced. This bootstrap path is not the live pointer stream: after portal consent the Selkies WebSocket input takes over. The dashboard's permission preview accepts only deliberate clicks on GNOME's consent dialog; it is **not** the live input surface. Its screenshot is non-draggable and moved pointers cannot send a stray click. The round selection marker appears only after keyboard arrow navigation, not as a fake GNOME cursor. Choose **Show live desktop** for window dragging and keyboard control after granting **Allow Remote Interaction** and **Share**. In the live Selkies iframe, GNOME's cursor PNG and hotspot are applied as the browser pointer; the viewer does not replace them with a generic crosshair. Phone zoom and preview navigation remain available; the app never blindly clicks the dialog. A local preference reopens straight into a previously approved desktop, while **Grant screen access** remains available for renewed consent. The embedded client in isolated dev decoded video and opened Files through browser input; back/reopen WebCodecs reconnection also passed.

### Trusted browser client and deployment choices

WebCodecs was unavailable in an opaque-origin sandbox (`AudioDecoder is not defined`), so the embedded iframe uses the **dashboard origin**. Its root HTML and executable Selkies client assets are copied from the SHA-256-pinned computer image into the trusted frontend image at build time; dev Caddy extracts them into ignored `.scratch/` before any computer starts. One frontend-only client-core adaptation checks both the original and resulting SHA-256 and allows *only* the JPEG/createImageBitmap path on insecure origins, skipping the unavailable HTTP AudioWorklet; the secure WebCodecs path is unchanged. A changed upstream package fails the build until reviewed. Guest-supplied HTML, JavaScript, file-browser pages, and unused API endpoints are denied by a UUID-scoped Caddy allowlist. Only an actual WebSocket Upgrade and the JSON status/health endpoints are proxied to that computer. Caddy forces JSON with `nosniff` and attachment on those guest-controlled responses, strips cookie/redirect headers, and serves previews as `image/jpeg` with `nosniff`; a plain GET to the WebSocket path returns 404. Built-in Selkies file transfers and printing are disabled; unsupported sharing/file/audio/gamepad/webcam/clipboard/sidebar controls are hidden, with audio, gamepad, webcam and clipboard transport disabled separately. An isolated E2E deliberately replaced a JavaScript asset with sudo *inside the disposable test computer* and confirmed the browser still received identical trusted bytes; arbitrary `/api/files/`, `/api/tokens`, `/api/sessions` and `/api/switch` were 404. `allow-same-origin` plus `allow-scripts` is **not** a sandbox security boundary: a vulnerability in the pinned client parsing untrusted media/JSON could access the dashboard API. Update the pinned client deliberately and keep the asset-provenance/endpoint regression checks. This trusted-network dashboard has no user authentication and must not be exposed publicly.

**Opt-in private-LAN HTTP/JPEG:** browser WebCodecs are unavailable on remote HTTP, so `compose.lan-http.yaml` builds a *separate* operator-approved `agent-swarm-default:http-jpeg` image with server-locked JPEG, while the frontend's audited client uses `createImageBitmap`. Supply a specific trusted private IPv4 `LAN_IP`; Compose publishes only loopback and that IPv4 on TCP 19090. Isolated dev at a genuinely insecure, non-localhost origin showed real 1920×1080 GNOME frames, mouse opening Files and Meta opening Overview. Twelve screenshot-polled key transitions had p50/p95 **218/221ms**, including screenshot/CDP overhead; this is not optical glass-to-glass or directly comparable with the WebCodecs frame-callback timing above. ## Computer limit and display mode

`COMPUTER_MAX_COUNT` (default 4, passed through Compose) is the most computers the controller lets you create. The Computers page shows how many are in use and disables **Create computer** at the limit; the controller still refuses a create over the limit with "Computer limit reached." and the backend drops the reservation it made.

Each computer reports its display server: images built from `x11.Dockerfile` carry the label `swarm.ng.display-server=x11` (older images are recognized by their `x11`/`xorg` tags). X11 computers have no screen-share consent step in the viewer; Wayland computers keep it. `VITE_COMPUTER_PORTAL_FREE` is now only the fallback for a controller that does not say.
