# Computers — lifecycle, previews and interactive desktop

Status: stage 1 lifecycle/previews and stage 2 interactive desktop passed isolated acceptance and were deployed to the trusted Tailnet dashboard. Stage 2 went live on 2026-09-25 using the existing Tailnet IPv4 **HTTP TCP 19090** with the JPEG/createImageBitmap fallback; browser WebCodecs/H.264 on non-localhost HTTP remains unavailable. The current live computer now uses opt-in GNOME/X11 without that portal dialog; a dedicated sandboxed browser verified actual Tailnet JPEG frames, GNOME cursor, window drag and keyboard input. Allowed Tailnet peers have direct control without a second GNOME grant.

## Terms and ownership

A **computer** is a persistent, shared Ubuntu GNOME environment, independent of agents and chat channels. No agent is assigned to or given tools for one by creating it. Its stable UUID, operator-chosen name, create-idempotency key and lifecycle state are saved in the platform's existing Prisma/SQLite database. Docker containers, named home/workspace volumes and a private network carry matching managed-resource labels. Docker is observed runtime state, not a replacement for the platform identity record.

**Create** reserves the identity first and uses its UUID for fixed Docker resource names. Repeating the same request key/name reuses that identity; a different name with the key is rejected. If provisioning fails, keep an operator-visible failed record and any owned partial resources; do not automatically delete possible user files. A GET after a backend crash reconciles a still-creating record with a running owned container, or marks it failed after the create deadline so it can be deleted by exact name. At most 100 platform computer records may be retained; existing idempotency keys still work at that cap. **Delete** requires the exact saved name at the API, checks Docker labels before touching any resource, then permanently removes the computer container, its own home/workspace volumes, egress sidecar and private network. A failed midway deletion remains retryable. It cannot remove an agent, chat, foreign container or unlabelled volume by supplying a name.

## Execution and isolation

The browser reaches one dashboard origin/port. Caddy/Vite forwards `/api` to the backend; the backend alone talks to an internal **computer controller**. Only that narrow controller mounts the root-equivalent Docker socket, without `.local` app data or provider credentials. The browser cannot choose an image, host mount, device, network flag or Docker API URL. Computers publish no per-computer host ports.

A computer runs with `sysbox-runc`, a user namespace, Docker's Chromium-compatible seccomp profile, CPU/memory/PID limits and only two owned named volumes. The non-root `ubuntu` user has **passwordless sudo inside the computer**; no Docker socket, host namespace, host cgroup bind, privileged mode or host filesystem mount is granted. `no-new-privileges` is intentionally not set on that sudo-capable computer because it would block setuid sudo. On the development host, Sysbox mapped computer UID 0 to unprivileged host UID 165536 and Chrome reported PID/network namespace and Seccomp-BPF sandboxing. This is observed host-specific behavior, not a universal claim that container root cannot exploit the kernel. If Sysbox is unavailable, creation must fail rather than fall back to privileged runc.

Each computer connects only to its own Docker bridge with `gateway_mode_ipv4=isolated`: Docker does not assign that bridge a host gateway address. A separate small **egress sidecar** sits outside the sudo-capable computer namespace, connects that private bridge to a shared public-egress bridge and filters forwarding before NAT. It permits public internet/DNS for browsers, apt and development; it rejects private/host/Docker/Tailnet/link-local destinations. Container root can change routes inside its namespace but cannot alter the gateway's firewall. The gateway must be filtered before the computer is started. Both workloads use no automatic Docker restart policy; controller recovery starts/validates egress before starting a stopped desktop, avoiding an unfiltered gateway start during host reboot. A normal Docker `--internal` bridge alone is **not sufficient**: a disposable probe reached its host gateway. The specific isolated-gateway + sidecar design passed public-web and deliberately reachable private-target probes, including gateway reject counters and an attempted root route change. Network and kernel isolation still require ongoing validation on each deployment host.

## Preview, status and limits

The Ubuntu GNOME 46 image boots a 1920×1080 headless Wayland virtual monitor and user PipeWire session. GNOME's direct Screenshot D-Bus interface refused external capture; the runtime instead keeps a Mutter ScreenCast `RecordMonitor` session alive and receives its PipeWire node. On demand, a bounded GStreamer PipeWire/JPEG pipeline produces a 480×270 image. Mutter's private API and its BGRA 1920×1080, variable 0/1 frame-rate caps are tied to the Ubuntu image version and need regression checks on upgrades. No interactive WebSocket/video session is opened for a grid card; the stage-2 Selkies listener inside a computer remains idle until a viewer connects. The browser requests screenshots at most every two seconds per visible card and stops when the card/tab is hidden; the controller coalesces concurrent preview requests and caches a frame briefly. In the isolated dev run, two independent computers returned real JPEG previews concurrently in about 0.22 seconds total (14,431 bytes each); this is a small-sample feasibility measurement, not a production latency/scale guarantee. A missing/stopped preview is indicated instead of presenting an old frame as live. The controller also reads bounded Docker CPU and memory statistics; transient stats failures yield unavailable values, not invented zeroes. If the controller itself is down, the API still lists saved platform computer identities with an unavailable state while disabling destructive/create actions; a disconnected backend must not make the computers appear deleted.

The UI keeps the existing Kibo-derived Basic Tabs navigation and typed Delete Confirmation dialog. Opening a computer hides the global tabs to give its viewer the full available height; the **Computers / Computer Name** breadcrumb remains and returns to the grid, restoring keyboard focus to the Computers tab. The desktop fits the browser width rather than panning unnecessarily on large screens, while narrow phones retain horizontal pan. The pinned client marks its JPEG canvases `crisp-edges` even when its fixed 1920×1080 desktop is shown smaller; the trusted viewer frame overrides only those canvases to browser-smooth interpolation. This is frontend-only presentation: it leaves source resolution, JPEG quality, input mapping, pinned executable bytes and the guest untouched. Smoothing removes forced nearest-neighbor pixel edges but cannot recover details lost to JPEG compression or downscaling. Dashboard routing and viewer scaling never change the guest display: the X11 runtime fixes **1920×1080**, Selkies has resize disabled, and the deployed Mutter logical monitor and text scale both report **1.0**. A viewer-requested larger size is ignored by the server. The X server's pre-existing `Xft.dpi` reports 192 despite Xvfb being launched with `-dpi 96`; no DPI/X resource is changed by this frontend work. The Kibo Image Card preview/source placed its title before the image, conflicting with the owner's chosen screenshot-first YouTube-like grid; that card composition is intentionally custom and retains the requested image → name → CPU/memory hierarchy without demo data or dependencies.

The lifecycle/preview milestone did not include agent assignment, console/tmux access, real-time input, clipboard/audio, multi-user login or interactive video. Current access policy is the trusted dashboard network: anyone allowed to open it may manage computers; **do not expose it publicly**. App-level user control is later scope.

## Interactive runtime (isolated E2E verified; Tailnet HTTP/JPEG deployed)

The stage-2 image pins the MPL-2.0 Selkies 2.0.0 Ubuntu 24.04 packages by amd64/arm64 SHA-256. **Selkies** supplies H.264 encoding, WebSocket transport, WebCodecs browser decode and mouse/keyboard input; WebRTC/TURN is intentionally not enabled because it would require additional relay TCP ports or a non-HTTP multiplexer. This stream is distinct from the sparse JPEG previews. It starts inside each managed GNOME computer, not in the backend's chat event loop, and does not publish a host port. GNOME's first-run RemoteDesktop portal needs explicit screen-sharing and remote-interaction consent. The portal's persistent restore token belongs to the computer's home volume, not the dashboard or any agent. Because headless GNOME has no session manager linking private video ports, the in-computer bridge identifies its own preview PipeWire node and links only the one other matching GNOME video output to Selkies's matching input; ambiguous capture sets fail closed. No Docker socket enters the computer. By default it also receives no host device; an operator may explicitly opt in to sharing only a validated `/dev/dri/renderDNNN` node through `COMPUTER_RENDER_DEVICE` for VA-API encoding. This shares the host GPU driver/kernel ioctl surface with a sudo-capable computer and is therefore a real additional trust decision, not an isolation guarantee. Card/modeset devices and arbitrary paths are rejected. This operator setting is checked against the actual device mapping on controller restart; if it changes for an existing computer, the controller **stops that desktop without deleting its home/workspace volumes** rather than silently retaining a revoked GPU grant. Restore the prior setting and restart the controller to re-open it, or arrange an explicit migration of that owned computer; changing Docker's existing device mount in place is not supported. The image has Mesa VA drivers and `vainfo`; without a render node Selkies falls back to software x264. Do not grant the whole `/dev/dri` directory or relax the browser seccomp profile to make GPU encoding work. A small, non-root **media relay** per computer copies encrypted TCP bytes from a shared, gateway-less Compose media bridge to **only that computer's private IP**. It has no Docker socket, host mounts, capabilities, writable root filesystem or published port. Its listener binds the address selected from the validated media subnet (interface numbering is not a security boundary); the computer cannot connect to either the media address or the relay's private address. The controller verifies its Docker ownership/alias and removes it before removing the computer. The namespaced Docker resource name can exceed DNS's 63-byte label limit, so Caddy dials a canonical `computer-<UUID>` alias scoped to that media bridge. Exact UUID-path routing and WebSocket proxying share the **sole external Caddy port** with the dashboard and API; interactive video packets never enter the backend chat event loop (the separate bounded consent JPEG does). A separate dev Caddy uses the same route snippet in front of Vite on loopback:5173. Caddy forwards the dashboard Host header for Selkies' same-origin WebSocket check and accepts only the computer's internal self-signed TLS on this isolated upstream. The H.264/WebCodecs path still requires a trusted HTTPS origin **on the same port** outside localhost. The deployed Tailnet HTTP/JPEG path below avoids WebCodecs without changing browser security flags; private-LAN HTTP is also available as an opt-in overlay.

For the original Wayland/portal mode (not the deployed X11 viewer), a **full-resolution, bounded, on-demand JPEG** uses the same private Mutter/PipeWire session as the small grid preview, but has a separate short cache and a 512 KiB image limit. A person viewing that computer can send a normalized one-click position; the backend checks the saved running computer, and the controller rechecks ownership/running state and coordinates where it executes a short-lived, non-root Mutter RemoteDesktop D-Bus session **inside only that computer**. No agent tool, host input device, raw command, automatic blind coordinate click, or separate computer port is introduced. This bootstrap path is not the live pointer stream: after portal consent the Selkies WebSocket input takes over. The dashboard's permission preview accepts only deliberate clicks on GNOME's consent dialog; it is **not** the live input surface. Its screenshot is non-draggable and moved pointers cannot send a stray click. The round selection marker appears only after keyboard arrow navigation, not as a fake GNOME cursor. Choose **Show live desktop** for window dragging and keyboard control after granting **Allow Remote Interaction** and **Share**. In the live Selkies iframe, GNOME's cursor PNG and hotspot are applied as the browser pointer; the viewer does not replace them with a generic crosshair. Phone zoom and preview navigation remain available; the app never blindly clicks the dialog. A local preference reopens straight into a previously approved desktop, while **Grant screen access** remains available for renewed consent. The embedded client in isolated dev decoded video and opened Files through browser input; back/reopen WebCodecs reconnection also passed.

On the actual isolated AMD64 development host, a disposable GNOME computer produced a 1920×1080 Selkies x264 stream at about 20 encoded frames per second, and a separate sandboxed Chromium browser decoded visible GNOME frames. Browser clicks opened Files and Meta opened GNOME Overview. One first frame was logged 14.8ms after its compositor timestamp; this is **not** glass-to-glass latency. A pinned ARM64 package exists, but its runtime was not tested. Separately, isolated dev API checks verified Selkies HTML and an HTTP 101 WebSocket upgrade through the existing dashboard port, two simultaneous computers, and denial of computer→media bridge/private-relay access. The embedded dashboard viewer then passed first-run portal consent with two user-initiated clicks, Chromium WebCodecs video at 1920×1080, browser pointer input opening Files, and a 320px phone surface with horizontal pan controls. Back/reopen reconnection and desktop keyboard toggling GNOME Overview subsequently passed the same isolated browser flow. A bounded input-to-decoded-video metric is reported below; the full 115-test browser regression suite passed; real Tailnet HTTPS deployment remains separately authorized and untested. The 2-CPU/4-GiB computer limit and software-encoding fallback remain. In a second isolated dev run with the one Radeon 680M render node, `vainfo` inside a non-root managed computer reported H.264/HEVC `EncSlice`, and Selkies chose **VAAPI H.264** while Chromium decoded 1920×1080. The first setup log advertised zero-copy rendering, but the real GNOME PipeWire portal supplied software frames and Selkies explicitly **demoted to readback encode**; do not describe the actual stream as zero-copy or assume a latency/CPU win without a comparison. The existing AMD Mesa driver logged a High-profile probe warning before selecting a usable VA-API profile. Twenty browser Meta-key/Overview transitions measured from input setup to the first matching decoded frame yielded **software x264 p50/p95 73.7/96.8ms** with Docker CPU **22.0/22.6%**, versus **VAAPI H.264 94.1/152.3ms** and **21.2/21.9%** on this host. These small synthetic runs include Playwright/CDP dispatch overhead and are **not optical glass-to-glass**, internet-loss, or production network measurements. With SHM readback, the GPU did not improve this low-latency workload, so hardware access stays opt-in rather than degrading the default for everyone. The live Tailnet stack now uses JPEG over HTTP on the one existing TCP port; the H.264/VA-API path remains an optional, undeployed HTTPS configuration. No agent receives computer tools by creating a computer.

### Trusted browser client and deployment choices

WebCodecs was unavailable in an opaque-origin sandbox (`AudioDecoder is not defined`), so the embedded iframe uses the **dashboard origin**. Its root HTML and executable Selkies client assets are copied from the SHA-256-pinned computer image into the trusted frontend image at build time; dev Caddy extracts them into ignored `.scratch/` before any computer starts. One frontend-only client-core adaptation checks both the original and resulting SHA-256 and allows *only* the JPEG/createImageBitmap path on insecure origins, skipping the unavailable HTTP AudioWorklet; the secure WebCodecs path is unchanged. A changed upstream package fails the build until reviewed. Guest-supplied HTML, JavaScript, file-browser pages, and unused API endpoints are denied by a UUID-scoped Caddy allowlist. Only an actual WebSocket Upgrade and the JSON status/health endpoints are proxied to that computer. Caddy forces JSON with `nosniff` and attachment on those guest-controlled responses, strips cookie/redirect headers, and serves previews as `image/jpeg` with `nosniff`; a plain GET to the WebSocket path returns 404. File transfers and printing are disabled; unsupported sharing/file/audio/gamepad/webcam/clipboard/sidebar controls are hidden, with audio, gamepad, webcam and clipboard transport disabled separately. An isolated E2E deliberately replaced a JavaScript asset with sudo *inside the disposable test computer* and confirmed the browser still received identical trusted bytes; arbitrary `/api/files/`, `/api/tokens`, `/api/sessions` and `/api/switch` were 404. `allow-same-origin` plus `allow-scripts` is **not** a sandbox security boundary: a vulnerability in the pinned client parsing untrusted media/JSON could access the dashboard API. Update the pinned client deliberately and keep the asset-provenance/endpoint regression checks. This trusted-network dashboard has no user authentication and must not be exposed publicly.

**Opt-in private-LAN HTTP/JPEG:** browser WebCodecs are unavailable on remote HTTP, so `compose.lan-http.yaml` builds a *separate* operator-approved `agent-swarm-default:http-jpeg` image with server-locked JPEG, while the frontend's audited client uses `createImageBitmap`. Supply a specific trusted private IPv4 `LAN_IP`; Compose publishes only loopback and that IPv4 on TCP 19090. Isolated dev at a genuinely insecure, non-localhost origin showed real 1920×1080 GNOME frames, mouse opening Files and Meta opening Overview. Twelve screenshot-polled key transitions had p50/p95 **218/221ms**, including screenshot/CDP overhead; this is not optical glass-to-glass or directly comparable with the WebCodecs frame-callback timing above. JPEG may increase bandwidth and CPU use compared with H.264; neither was measured for this fallback, and it has not been tested on a live LAN or phone. **There is no platform user authentication and HTTP video/input/API traffic is unencrypted on the LAN.** Never bind `0.0.0.0` or a public address based merely on this example; access scope and risk are the operator's explicit decision. This LAN overlay remains undeployed; the live Tailnet migration is described below.

**Original Wayland Tailnet HTTP/JPEG (rollback option):** `compose.tailscale-http-jpeg.yaml` combines with `compose.yaml` + `compose.tailscale.yaml` to keep the existing loopback/Tailnet **TCP 19090** binds and persistent `.local` mount, but select the JPEG-only image. Tailscale encrypts packets between devices while the browser still sees HTTP and uses `createImageBitmap`, not WebCodecs. The dashboard remains unauthenticated to any allowed Tailnet peer. This original Wayland variant previously ran on the Tailnet IPv4: loopback and Tailnet TCP19090 were its only published app bindings. After the owner's restart approval, the existing computer was migrated to the JPEG image; its identity, named home/workspace volumes and files survived, and a mode-0600 `.local` archive, separate volume archives and local image rollback tags were retained. Dashboard health, a WebSocket HTTP 101 upgrade, pinned trusted core bytes and media/API allowlists passed live checks. A fresh automation browser confirmed the remote HTTP origin is insecure and the create dialog is centered at 1280px and 320px, without creating a computer. The portal-based viewer remained view-only after GNOME denied its input devices; the subsequent X11 migration below replaced it without changing the computer identity or volumes.

## Development verification and cleanup

Build approved managed images with `docker build -t <fixed-tag> ...` before creating computers, **not `docker compose build` under a disposable project**: Compose image metadata is inherited by Docker-created guest/gateway/media containers and can make a live resource look test-owned to cleanup tooling. The controller refuses to create a resource from any image carrying `com.docker.compose.*` labels. The controller will not build arbitrary browser-supplied images. Controller image/configuration is separate from the main backend so the Docker socket is never mounted alongside `.local` credentials. Use a unique Compose project and `COMPUTER_NAMESPACE` in isolated dev tests, separate from the live `.local` mount. The opt-in Linux harness `sh scripts/test-computers-dev.sh` builds these images, starts a unique dev Compose project on loopback port 5173, exercises the real API and one sandboxed browser worker (`--workers=1 --retries=0`), and removes only its own test containers/volumes/networks on exit. It refuses an already occupied port or an existing test namespace. Do not run the live browser spec against a production dashboard. Clean up only test-labelled resources, never broad-prune Docker or remove the older v2 project.
