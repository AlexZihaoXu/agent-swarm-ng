# Computers — lifecycle, previews and interactive desktop

Status: stage 1 lifecycle and passive previews passed isolated development API/browser E2E, merged into local `main` and were deployed to the trusted Tailnet dashboard on 2026-09-24. Stage 2 interactive desktop passed isolated development tests and is available in local source. It was **not** deployed to the Tailnet; the live stack remains at stage 1.

## Terms and ownership

A **computer** is a persistent, shared Ubuntu GNOME environment, independent of agents and chat channels. No agent is assigned to or given tools for one by creating it. Its stable UUID, operator-chosen name, create-idempotency key and lifecycle state are saved in the platform's existing Prisma/SQLite database. Docker containers, named home/workspace volumes and a private network carry matching managed-resource labels. Docker is observed runtime state, not a replacement for the platform identity record.

**Create** reserves the identity first and uses its UUID for fixed Docker resource names. Repeating the same request key/name reuses that identity; a different name with the key is rejected. If provisioning fails, keep an operator-visible failed record and any owned partial resources; do not automatically delete possible user files. A GET after a backend crash reconciles a still-creating record with a running owned container, or marks it failed after the create deadline so it can be deleted by exact name. At most 100 platform computer records may be retained; existing idempotency keys still work at that cap. **Delete** requires the exact saved name at the API, checks Docker labels before touching any resource, then permanently removes the computer container, its own home/workspace volumes, egress sidecar and private network. A failed midway deletion remains retryable. It cannot remove an agent, chat, foreign container or unlabelled volume by supplying a name.

## Execution and isolation

The browser reaches one dashboard origin/port. Caddy/Vite forwards `/api` to the backend; the backend alone talks to an internal **computer controller**. Only that narrow controller mounts the root-equivalent Docker socket, without `.local` app data or provider credentials. The browser cannot choose an image, host mount, device, network flag or Docker API URL. Computers publish no per-computer host ports.

A computer runs with `sysbox-runc`, a user namespace, Docker's Chromium-compatible seccomp profile, CPU/memory/PID limits and only two owned named volumes. The non-root `ubuntu` user has **passwordless sudo inside the computer**; no Docker socket, host namespace, host cgroup bind, privileged mode or host filesystem mount is granted. `no-new-privileges` is intentionally not set on that sudo-capable computer because it would block setuid sudo. On the development host, Sysbox mapped computer UID 0 to unprivileged host UID 165536 and Chrome reported PID/network namespace and Seccomp-BPF sandboxing. This is observed host-specific behavior, not a universal claim that container root cannot exploit the kernel. If Sysbox is unavailable, creation must fail rather than fall back to privileged runc.

Each computer connects only to its own Docker bridge with `gateway_mode_ipv4=isolated`: Docker does not assign that bridge a host gateway address. A separate small **egress sidecar** sits outside the sudo-capable computer namespace, connects that private bridge to a shared public-egress bridge and filters forwarding before NAT. It permits public internet/DNS for browsers, apt and development; it rejects private/host/Docker/Tailnet/link-local destinations. Container root can change routes inside its namespace but cannot alter the gateway's firewall. The gateway must be filtered before the computer is started. Both workloads use no automatic Docker restart policy; controller recovery starts/validates egress before starting a stopped desktop, avoiding an unfiltered gateway start during host reboot. A normal Docker `--internal` bridge alone is **not sufficient**: a disposable probe reached its host gateway. The specific isolated-gateway + sidecar design passed public-web and deliberately reachable private-target probes, including gateway reject counters and an attempted root route change. Network and kernel isolation still require ongoing validation on each deployment host.

## Preview, status and limits

The Ubuntu GNOME 46 image boots a 1920×1080 headless Wayland virtual monitor and user PipeWire session. GNOME's direct Screenshot D-Bus interface refused external capture; the runtime instead keeps a Mutter ScreenCast `RecordMonitor` session alive and receives its PipeWire node. On demand, a bounded GStreamer PipeWire/JPEG pipeline produces a 480×270 image. Mutter's private API and its BGRA 1920×1080, variable 0/1 frame-rate caps are tied to the Ubuntu image version and need regression checks on upgrades. No interactive WebSocket/video session is opened for a grid card; the stage-2 Selkies listener inside a computer remains idle until a viewer connects. The browser requests screenshots at most every two seconds per visible card and stops when the card/tab is hidden; the controller coalesces concurrent preview requests and caches a frame briefly. In the isolated dev run, two independent computers returned real JPEG previews concurrently in about 0.22 seconds total (14,431 bytes each); this is a small-sample feasibility measurement, not a production latency/scale guarantee. A missing/stopped preview is indicated instead of presenting an old frame as live. The controller also reads bounded Docker CPU and memory statistics; transient stats failures yield unavailable values, not invented zeroes. If the controller itself is down, the API still lists saved platform computer identities with an unavailable state while disabling destructive/create actions; a disconnected backend must not make the computers appear deleted.

The UI keeps the existing Kibo-derived Basic Tabs navigation and typed Delete Confirmation dialog. The Kibo Image Card preview/source placed its title before the image, conflicting with the owner's chosen screenshot-first YouTube-like grid; that card composition is intentionally custom and retains the requested image → name → CPU/memory hierarchy without demo data or dependencies.

The lifecycle/preview milestone did not include agent assignment, console/tmux access, real-time input, clipboard/audio, multi-user login or interactive video. Current access policy is the trusted dashboard network: anyone allowed to open it may manage computers; **do not expose it publicly**. App-level user control is later scope.

## Interactive runtime (isolated development verified, not live deployed)

The stage-2 image pins the MPL-2.0 Selkies 2.0.0 Ubuntu 24.04 packages by amd64/arm64 SHA-256. **Selkies** supplies H.264 encoding, WebSocket transport, WebCodecs browser decode and mouse/keyboard input; WebRTC/TURN is intentionally not enabled because it would require additional relay TCP ports or a non-HTTP multiplexer. This stream is distinct from the sparse JPEG previews. It starts inside each managed GNOME computer, not in the backend's chat event loop, and does not publish a host port. GNOME's first-run RemoteDesktop portal needs explicit screen-sharing and remote-interaction consent. The portal's persistent restore token belongs to the computer's home volume, not the dashboard or any agent. Because headless GNOME has no session manager linking private video ports, the in-computer bridge identifies its own preview PipeWire node and links only the one other matching GNOME video output to Selkies's matching input; ambiguous capture sets fail closed. No Docker socket enters the computer. By default it also receives no host device; an operator may explicitly opt in to sharing only a validated `/dev/dri/renderDNNN` node through `COMPUTER_RENDER_DEVICE` for VA-API encoding. This shares the host GPU driver/kernel ioctl surface with a sudo-capable computer and is therefore a real additional trust decision, not an isolation guarantee. Card/modeset devices and arbitrary paths are rejected. This operator setting is checked against the actual device mapping on controller restart; if it changes for an existing computer, the controller **stops that desktop without deleting its home/workspace volumes** rather than silently retaining a revoked GPU grant. Restore the prior setting and restart the controller to re-open it, or arrange an explicit migration of that owned computer; changing Docker's existing device mount in place is not supported. The image has Mesa VA drivers and `vainfo`; without a render node Selkies falls back to software x264. Do not grant the whole `/dev/dri` directory or relax the browser seccomp profile to make GPU encoding work. A small, non-root **media relay** per computer copies encrypted TCP bytes from a shared, gateway-less Compose media bridge to **only that computer's private IP**. It has no Docker socket, host mounts, capabilities, writable root filesystem or published port. Its listener binds the address selected from the validated media subnet (interface numbering is not a security boundary); the computer cannot connect to either the media address or the relay's private address. The controller verifies its Docker ownership/alias and removes it before removing the computer. The namespaced Docker resource name can exceed DNS's 63-byte label limit, so Caddy dials a canonical `computer-<UUID>` alias scoped to that media bridge. Exact UUID-path routing and WebSocket proxying share the **sole external Caddy port** with the dashboard and API; interactive video packets never enter the backend chat event loop (the separate bounded consent JPEG does). A separate dev Caddy uses the same route snippet in front of Vite on loopback:5173. Caddy forwards the dashboard Host header for Selkies' same-origin WebSocket check and accepts only the computer's internal self-signed TLS on this isolated upstream. The external Tailnet dashboard still requires a trusted HTTPS certificate **on the same port** for WebCodecs on non-localhost origins. No live Tailnet certificate was issued or deployed.

For the first GNOME portal grant, a **full-resolution, bounded, on-demand JPEG** uses the same private Mutter/PipeWire session as the small grid preview, but has a separate short cache and a 512 KiB image limit. A person viewing that computer can send a normalized one-click position; the backend checks the saved running computer, and the controller rechecks ownership/running state and coordinates where it executes a short-lived, non-root Mutter RemoteDesktop D-Bus session **inside only that computer**. No agent tool, host input device, raw command, automatic blind coordinate click, or separate computer port is introduced. This bootstrap path is not the live pointer stream: after portal consent the Selkies WebSocket input takes over. The dashboard viewer now exposes the preview with pointer and keyboard crosshair clicks, zoom on phones, and an explicit **Show live desktop** action; it never blindly clicks the dialog. A local preference reopens straight into a previously approved desktop, while **Grant screen access** remains available for renewed consent. The embedded client in isolated dev decoded video and opened Files through browser input; back/reopen WebCodecs reconnection also passed.

On the actual isolated AMD64 development host, a disposable GNOME computer produced a 1920×1080 Selkies x264 stream at about 20 encoded frames per second, and a separate sandboxed Chromium browser decoded visible GNOME frames. Browser clicks opened Files and Meta opened GNOME Overview. One first frame was logged 14.8ms after its compositor timestamp; this is **not** glass-to-glass latency. A pinned ARM64 package exists, but its runtime was not tested. Separately, isolated dev API checks verified Selkies HTML and an HTTP 101 WebSocket upgrade through the existing dashboard port, two simultaneous computers, and denial of computer→media bridge/private-relay access. The embedded dashboard viewer then passed first-run portal consent with two user-initiated clicks, Chromium WebCodecs video at 1920×1080, browser pointer input opening Files, and a 320px phone surface with horizontal pan controls. Back/reopen reconnection and desktop keyboard toggling GNOME Overview subsequently passed the same isolated browser flow. A bounded input-to-decoded-video metric is reported below; the full 115-test browser regression suite passed; real Tailnet HTTPS deployment remains separately authorized and untested. The 2-CPU/4-GiB computer limit and software-encoding fallback remain. In a second isolated dev run with the one Radeon 680M render node, `vainfo` inside a non-root managed computer reported H.264/HEVC `EncSlice`, and Selkies chose **VAAPI H.264** while Chromium decoded 1920×1080. The first setup log advertised zero-copy rendering, but the real GNOME PipeWire portal supplied software frames and Selkies explicitly **demoted to readback encode**; do not describe the actual stream as zero-copy or assume a latency/CPU win without a comparison. The existing AMD Mesa driver logged a High-profile probe warning before selecting a usable VA-API profile. Twenty browser Meta-key/Overview transitions measured from input setup to the first matching decoded frame yielded **software x264 p50/p95 73.7/96.8ms** with Docker CPU **22.0/22.6%**, versus **VAAPI H.264 94.1/152.3ms** and **21.2/21.9%** on this host. These small synthetic runs include Playwright/CDP dispatch overhead and are **not optical glass-to-glass**, internet-loss, or production network measurements. With SHM readback, the GPU did not improve this low-latency workload, so hardware access stays opt-in rather than degrading the default for everyone. The current live Tailnet deployment retains stage 1 only. No agent receives computer tools by creating a computer.

### Trusted browser client and future Tailnet HTTPS

WebCodecs was unavailable in an opaque-origin sandbox (`AudioDecoder is not defined`), so the embedded iframe uses the **dashboard origin**. Its root HTML and all executable Selkies client assets are copied from the SHA-256-pinned computer image into the trusted frontend image at build time; dev Caddy copies the same bytes into ignored `.scratch/` before any computer starts. Guest-supplied HTML, JavaScript, file-browser pages, and unused API endpoints are denied by a UUID-scoped Caddy allowlist. Only an actual WebSocket Upgrade and the JSON status/health endpoints are proxied to that computer. Caddy forces JSON with `nosniff` and attachment on those guest-controlled responses, strips cookie/redirect headers, and serves previews as `image/jpeg` with `nosniff`; a plain GET to the WebSocket path returns 404. File transfers and printing are disabled; unsupported sharing/file/audio/gamepad/webcam/clipboard/sidebar controls are hidden, with audio, gamepad, webcam and clipboard transport disabled separately. An isolated E2E deliberately replaced a JavaScript asset with sudo *inside the disposable test computer* and confirmed the browser still received identical trusted bytes; arbitrary `/api/files/`, `/api/tokens`, `/api/sessions` and `/api/switch` were 404. `allow-same-origin` plus `allow-scripts` is **not** a sandbox security boundary: a vulnerability in the pinned client parsing untrusted media/JSON could access the dashboard API. Update the pinned client deliberately and keep the asset-provenance/endpoint regression checks. This trusted-network dashboard has no user authentication and must not be exposed publicly.

The owner authorized a stage-2 Tailnet rollout, but it is **paused**: Tailscale currently responds `your Tailscale account does not support getting TLS certs`, and a running stage-1 computer needs a coordinated desktop restart to migrate its image without deleting home/workspace volumes. Do not deploy the viewer over HTTP or silently replace that computer. Once trusted certificates are enabled and the restart is agreed, combine `compose.yaml`, `compose.tailscale.yaml`, and `compose.tailscale-https.yaml`. Provision a trusted certificate for this machine's Tailnet DNS name with Tailscale's certificate facility into project-local, access-restricted `.local/certs/tailnet.crt` and `.local/certs/tailnet.key`; configure `TAILSCALE_DNS_NAME` and the existing `TAILSCALE_IP`. The optional override mounts only those files read-only into Caddy and terminates HTTPS on the **existing Tailnet TCP 19090**; it opens neither a public port nor UDP/443 or per-computer ports. Caddy config adaptation verified a sole `:19090` listener and file-based certificate loading, but a real Tailnet certificate/browser test has **not** been run and no stage-2 live deployment was performed. File-based Tailnet certificates expire; renew the cert/key and reload Caddy before expiry when deployment is unblocked. Build the approved stage-2 computer image **before** the production frontend image because the frontend copies its immutable client assets from that local image. An operator may separately set `COMPUTER_RENDER_DEVICE=/dev/dri/renderD128` on this tested AMD host; leave it unset elsewhere until validated.

## Development verification and cleanup

Build the approved images explicitly before creating computers (default template and `templates/default/egress.Dockerfile`); the controller will not build arbitrary browser-supplied images. Controller image/configuration is separate from the main backend so the Docker socket is never mounted alongside `.local` credentials. Use a unique Compose project and `COMPUTER_NAMESPACE` in isolated dev tests, separate from the live `.local` mount. The opt-in Linux harness `sh scripts/test-computers-dev.sh` builds these images, starts a unique dev Compose project on loopback port 5173, exercises the real API and one sandboxed browser worker (`--workers=1 --retries=0`), and removes only its own test containers/volumes/networks on exit. It refuses an already occupied port or an existing test namespace. Do not run the live browser spec against a production dashboard. Clean up only test-labelled resources, never broad-prune Docker or remove the older v2 project. The disposable probes recorded in `.scratch/tickets/computers-dashboard.md` verified a real GNOME JPEG, passwordless sudo, Chrome sandbox report, public egress/private rejection, named-volume persistence across container replacement, controller create/list/preview/delete and controller restart recovery. A separate real API exercise through only the dev frontend port verified saved identity after a backend restart, wrong-name refusal and complete data-volume deletion. The opt-in harness then passed real API and browser create/preview/delete end-to-end, passwordless `sudo apt-get update`, two-computer private-network separation with a reachable test target, and parallel previews. It removed every test-labelled/Compose container, network and volume in its namespace. The full 112-test browser regression suite passed after the UI consistency fixes, including 280px/reduced-motion checks.
